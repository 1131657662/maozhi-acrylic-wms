# 升级与重构提案

本轮只产出提案和文档，不改业务代码。提案依据旧 ERP 页面/控制器、当前原型、真实样本统计和现有 E2E；提案中的目标值是验收指标，不代表已经实现。所有代码证据均复核到文件现有行范围，并提供可点击行链接；新提案目标需实测，不以设计稿代替验收。

## 升级

### U-01 统一查询壳与服务端筛选

**现状与证据**

旧 ERP 的入库单列表已经有筛选抽屉、批量操作和导出，但入口与列表状态分散：[InboundOrderList.vue（634–678、790–981 行）](D:/wms-new/wms-frontend-pure/src/views/wms/InboundOrderList.vue#L634)；出库列表同样重复一套筛选和批量逻辑：[OutboundOrderList.vue（643–691、799–981 行）](D:/wms-new/wms-frontend-pure/src/views/wms/OutboundOrderList.vue#L643)。当前原型入库和出库列表都显式 `search={false}`，只保留单号关键词/状态：[inbound/list.tsx（44–69 行）](../apps/web/src/features/inbound/list.tsx#L44)、[outbound/list.tsx（61–108 行）](../apps/web/src/features/outbound/list.tsx#L61)。

**方案 A 与方案 B**

- 方案 A（推荐）：做一个 ProTable 列表壳，筛选条件统一为日期范围、状态、仓库、往来单位、单号；条件通过 API 下推，列显隐和筛选保存在 localStorage。优点是重复代码少、万级数据可控；成本是需要统一接口参数。
- 方案 B：保留每页独立列表，只增加搜索字段。优点是初期改动小；缺点是筛选语义和空/错态会继续漂移，后续导出要重复维护。

推荐 A，因为它直接解决当前两个列表的重复实现，并且是导出、报表和日志查询的共同基础。

**收益假设**

旧系统“打开列表→打开筛选→填条件→查询”至少 4 个动作，新方案目标为首屏填完条件后 2 个动作完成查询；10,000 行数据翻页 p95 <500ms，首屏 p95 <1.5s。测量方式：Playwright 记录点击/键盘动作；脚本向本地 MySQL 生成 10,000 行临时数据并记录 API p50/p95；当前原型基线为 1 个关键词 + 1 个状态控件，完整多条件时延待实测。

**风险与回退**

查询参数错映射会返回错误集合；通过接口契约测试逐个字段核对，发现问题时回退到原查询端点。localStorage 结构带版本号，升级失败清除该页筛选而不影响数据。

### U-02 RK/CK 自动单号与草稿键盘流

**现状与证据**

旧 ERP 已有编号生成器：[bill_no.js:11](D:/wms-new/wms-backend/utils/bill_no.js#L11)。提案基线中两个表单各需手填一次；B1a 第 1 提交已改为服务端取号：[inbound/editor.tsx:80](../apps/web/src/features/inbound/editor.tsx#L80)、[outbound/editor.tsx:105](../apps/web/src/features/outbound/editor.tsx#L105)。现行 E2E 验证自动号与编辑保号：[outbound.spec.ts:76](../tests/e2e/outbound.spec.ts#L76)。

**方案 A 与方案 B**

- 方案 A（推荐）：服务端事务生成 `RK-YYYYMMDD-####` 和 `CK-YYYYMMDD-####`，与业务单/幂等结果一起提交；配置页提供服务端非占号预览，最终号以创建成功响应为准。草稿、`Ctrl+S`、`Esc` 留后续批次，不纳入本提交。
- 方案 B：前端自行按日期计算预览。成本较低，但不了解历史占号和服务器业务日，不能作为权威取号；两方案均不承诺并发下预览等于最终号。

推荐 A；业务已决定入库/出库使用独立前缀，不能继续沿用手填。

**收益假设**

建单各少 1 个手填字段。实测两类各 50 个并发 HTTP 创建，唯一率 100%，重复号 0：[numbering-concurrency.test.ts](../apps/api/tests/numbering-concurrency.test.ts)。两屏/键盘时长仍待实测，不把当前创建称为草稿。

**风险与回退**

首次按完整格式的历史最大序号初始化（含软删、不同补零宽度）；不能解析的历史号保留。每次候选号再精确查两类单据，冲突立即报错，不循环猜号。修改宽度只改补零，保存前碰撞/容量校验；事务失败同时回滚计数器，未提交的号未被消耗。旧客户端原号兼容且响应标记弃用，不静默换号。回退须同时回退 Web/API；非空 004 表保留，不执行 down，不承诺不存在的配置开关。

### U-03 入库重量校验与出库事实确认分层

**现状与证据**

样本重量范围 60–389.5kg，9018/9018 条码重量一致，说明统一件重反算不成立：[sku-analysis.json](../.local/prod-sample/sku-analysis.json)。当前入库表单已分别录包数和总吨数：[inbound/editor.tsx（112–123 行）](../apps/web/src/features/inbound/editor.tsx#L112)，但没有汇总差异提示。旧 ERP 入库审核会在同一动作中更新库存：[inbound_order.js（456–545 行）](D:/wms-new/wms-backend/controllers/inbound_order.js#L456)；当前出库则已把 PDA 事实与 Web 确认拆开：[confirm.ts（25–36 行）](../apps/api/src/features/outbound/confirm.ts#L25)。

**方案 A 与方案 B**

- 方案 A（推荐）：入库在同一表单即时显示包数/吨数合计和字段级错误；出库详情保留“扫码事实→冻结→Web 确认”三段，并在确认抽屉显示包级实重、库存前后值。优点是既不丢重量事实，又能防误扣。
- 方案 B：只在提交后由后端返回汇总错误，详情仍沿用一个审核按钮。优点是开发快；缺点是错误发现晚，且审核语义继续混杂。

推荐 A，因为它保留现有库存事务/幂等语义，并把错误前移到录入现场。

归属已定：入库审核/明确确认是正向库存边界，放 **B1a 第 3 提交**；撤销审核、作废、更正放 **B2**，需补偿流水及后续出库依赖校验，不可只改状态或删原流水。**B1b 不承接业务状态机**。第 1 提交维持现有登记即确认行为，不宣称审核已补齐。

**收益假设**

目标是重量/包数不一致时 0 次静默提交，重复确认 0 次重复扣减；出库确认前核对由跨页查找降为详情 1 屏。测量方式：E2E 构造 10 个重量差异和 3 次重复确认；比对库存、流水和审计；当前原型已覆盖重复确认幂等，差异提示耗时待实测。

**风险与回退**

汇总校验过严会阻断历史异常单；对历史数据只警示不阻断，对新单按配置启用硬校验。确认抽屉异常时事务回滚，保留 PDA 原事实，回退到旧确认按钮只允许在 feature flag 下用于测试。

### U-04 未知状态/流水类型原文回退与用途隔离

**现状与证据**

样本中单据状态为 `audited` 114/115（入库）、`audited` 414/415（出库）；流水类型为 `check` 47、`import` 60、`inbound` 182、`outbound` 539，且有 24 条软删：[prod-sample CSV 汇总](../.local/prod-sample/manifest.json)。基线只有出库部分映射；B1a 第 1 提交改为共享 [StatusTag](../apps/web/src/components/StatusTag/index.tsx#L1) 与 [JournalTypeTag](../apps/web/src/components/JournalTypeTag/index.tsx#L1)。

**方案 A 与方案 B**

- 方案 A（采用）：保留数据库原字符串，统一 `StatusTag`/`JournalTypeTag`；未知状态用“状态待识别：原文”灰色标签，详情常驻说明未知含义、核对原单的方法及出库确认禁用。库存业务前提已纠正为用途隔离：库存与单据只认 erp-product，固定 ERP 视图；sku-spec 只属于 B1c 条码目录页面，未归属仅诊断日志，无库存入口或占位。保留 API 来源参数守卫和严格契约；报表尚未实现，后续只统计 ERP。
- 方案 B：导入时把未知值映射到有限枚举。优点是页面更简单；缺点是历史语义不可逆，审计和报表会失真。

推荐 A，符合真实数据保留原值的决定。

**收益假设**

目标页面状态空白数 0、未知值报错数 0；用户无需回到数据库确认原值。测量方式：E2E 注入 `future_status`/`future_type` fixture，遍历列表、详情、流水和报表；当前基线只覆盖已知出库标签，未知值覆盖率待实测。

**风险与回退**

标签文案错误不会改变数据，但可能误导用户；未知值保留原文，不猜中文含义，关键说明不藏在 tooltip 中。第 2 批无需数据迁移，应用代码可回退；旧 `/stock` 数组保持兼容。SPEC 是扫码目录而非库存；验收固定 ERP 视图、无目录库存入口/请求/占位。原非 ERP 测试数据仅作异常夹具验证守卫，不代表业务库存。

### U-05 备份产物校验与恢复演练

**现状与证据**

当前备份脚本检查本地数据库身份并生成 SQL 文件，但没有产物摘要/大小清单或完成后校验：[backup.ts（7–29 行）](../scripts/backup.ts#L7)。恢复脚本会恢复到新库、校验库身份并在失败时清理本次新库，但没有校验和检查或数据级完整性对账：[restore.ts（7–28 行）](../scripts/restore.ts#L7)。操作日志由审计函数写入事务：[audit.ts（6–10 行）](../apps/api/src/shared/audit.ts#L6)。

**方案 A 与方案 B**

- 方案 A（推荐）：备份完成后写 SHA-256、文件大小、数据库身份和时间 manifest；恢复前校验摘要，导入新库后运行表行数、关键重量汇总和身份检查；通过后仍由人显式切换，失败只清理本次隔离恢复库。
- 方案 B：只定期人工运行 `npm run restore`，人工抽查若干页面。优点是实现成本低；缺点是无法发现备份截断或样本之外的数据缺失，恢复结果依赖操作者记忆。

推荐 A。它验证“能恢复且内容一致”，不改变当前库、不连接生产，也不把审计日志当审批流程。

**收益假设**

每个备份产物都有可验证摘要的比例 100%；每次恢复演练执行行数/重量对账；损坏文件在导入前拒绝；隔离恢复库端到端恢复目标 <15 分钟，当前恢复时长待实测。测量方式：对 SQL 文件做单字节篡改、执行本地恢复演练并核对 manifest、指定表计数与总重量；每次迁移验收前至少跑一次。

**风险与回退**

摘要只能证明文件未变化，不能单独证明数据逻辑完整，因此恢复后仍须跑数据对账。校验/导入失败只删除本次随机命名的恢复库，原开发库和备份文件保留；如果自动核对脚本有误，可回退到人工只读对账，不自动切换数据库。

## 优化

### O-01 列表信息密度、响应式和固定列

**现状与证据**

当前出库表已有固定状态/操作列和列显隐持久化：[outbound/list.tsx（21–34、76–77 行）](../apps/web/src/features/outbound/list.tsx#L21)，但入库表没有固定操作列且两个列表通过 `scroll.x` 硬撑：[inbound/list.tsx（44–52 行）](../apps/web/src/features/inbound/list.tsx#L44)。旧 StockList 同时放置库存重建、重置和清零等高风险按钮：[StockList.vue（777–816 行）](D:/wms-new/wms-frontend-pure/src/views/wms/StockList.vue#L777)。

**方案 A 与方案 B**

- 方案 A（推荐）：1440/1280 使用关键列左固定、操作列右固定，次要列进入列设置；1280 以下筛选折叠为抽屉，表格保持页面无横向滚动，危险库存操作移入明确原因抽屉。
- 方案 B：所有列保留，依赖横向滚动。优点是信息一次展示；缺点是关键字段和操作会离开视口，现场误操作概率更高。

推荐 A，符合 ProTable 和现有响应式约束。

**收益假设**

200 行列表仍能扫读关键列，主要操作在首屏可见；1280/1440 页面级横向滚动 0。测量方式：Playwright 两个 viewport 断言 `scrollWidth <= innerWidth`，记录首屏操作可见性；当前 1280 E2E 已有布局断言，列固定策略待实测。

**风险与回退**

固定列宽设置过大可能压缩内容；为列设置定义最小/最大宽度并允许用户恢复默认。响应式折叠异常时回退为桌面布局，不改变数据接口。

### O-02 页面、导出、打印共用字段定义

**现状与证据**

旧 ERP 列表导出和详情导出分开实现：入库列表 [InboundOrderList.vue（444–537 行）](D:/wms-new/wms-frontend-pure/src/views/wms/InboundOrderList.vue#L444)、入库详情 [InboundOrderDetail.vue（107–148 行）](D:/wms-new/wms-frontend-pure/src/views/wms/InboundOrderDetail.vue#L107)；出库同样有列表/详情两套导出。当前原型没有导出和打印组件。

**方案 A 与方案 B**

- 方案 A（推荐）：为每个业务列表定义一份字段 schema，ProTable、CSV/Excel、打印模板都从 schema 生成；CSV 使用 UTF-8 BOM，Excel/打印保留同一列顺序和合计。
- 方案 B：页面、导出、打印各写一份字段映射。优点是局部灵活；缺点是字段变更容易漏改，出现屏幕与打印不一致。

推荐 A，减少长期维护成本。

**收益假设**

同一单据屏幕/导出/打印字段差异 0；筛选到导出 ≤3 步，10,000 行分页导出不占满浏览器内存。测量方式：脚本比较字段 schema、导出表头和打印 DOM；导出大数据时记录内存与耗时；均待实测。

**风险与回退**

历史字段缺失时显示空值并保留列，不改变历史记录；schema 生成器出错时可下载原始 CSV，打印仍可用基础模板。

### O-03 输入恢复与键盘路径

**现状与证据**

旧入/出库表单将表头、客户/供应商、车辆、明细拆在长页面：[InboundOrderForm.vue（354–560 行）](D:/wms-new/wms-frontend-pure/src/views/wms/InboundOrderForm.vue#L354)、[OutboundOrderForm.vue（427–749 行）](D:/wms-new/wms-frontend-pure/src/views/wms/OutboundOrderForm.vue#L427)。当前 ProForm 已有字段级规则，但错误只通过 Alert 展示：[inbound/editor.tsx（64–65 行）](../apps/web/src/features/inbound/editor.tsx#L64)、[outbound/editor.tsx:88](../apps/web/src/features/outbound/editor.tsx#L88)。

**方案 A 与方案 B**

- 方案 A（推荐）：表单按“单据头/明细/合计”分组，回车跳到下一字段，Ctrl+S 保存，Esc 返回；失败时保留表单值并滚动到第一个错误。
- 方案 B：继续使用默认 ProForm 提交，只增加错误 toast。优点是改动小；缺点是现场录入需要鼠标找错，网络失败容易重复提交。

**风险与回退**

快捷键可能与浏览器冲突，输入框内只在无组合输入时生效；快捷键异常可关闭 feature flag，保留鼠标操作。

### O-04 PDA 连续扫码与离线补传反馈

**现状与证据**

PDA 已在本机持久化扫码事实、断网后保留并重试，不能把这些已有能力误报为缺失：[ScanRepository.kt（8–23 行）](../apps/pda/app/src/main/java/cn/maozhi/wms/pda/scan/ScanRepository.kt#L8)、[SyncWorker.kt（19–33 行）](../apps/pda/app/src/main/java/cn/maozhi/wms/pda/sync/SyncWorker.kt#L19)。扫码页显示服务端与待处理总数，但扫码、记录、补传分成独立操作，未逐条显示失败/冲突原因：[ScanScreen.kt（23–36 行）](../apps/pda/app/src/main/java/cn/maozhi/wms/pda/ui/ScanScreen.kt#L23)。同步当前遇到第一个失败事实就退出本轮：[SyncRepository.kt（11–24 行）](../apps/pda/app/src/main/java/cn/maozhi/wms/pda/scan/SyncRepository.kt#L11)。仪器测试已覆盖重开数据库后队列仍存在及扫码冻结不扣库存：[ScanIntegrationTest.kt（21–44 行）](../apps/pda/app/src/androidTest/java/cn/maozhi/wms/pda/ScanIntegrationTest.kt#L21)。

**方案 A 与方案 B**

- 方案 A（推荐）：扫码主屏保留焦点和连续扫码；在进度区拆分“待补传/失败/冲突/已回传”，显示最后一条结果及原因；网络错误自动重试，业务冲突停在可核对记录，不删除或改写 UUID/正文。优点是现场不用离开扫码主流程，也能知道哪些事实尚未到服务器。
- 方案 B：保留当前主屏，把状态和处理全部放在“扫码记录”页。优点是扫码页更简单；缺点是现场需切页判断是否漏传，无法快速发现冲突。

推荐 A。Miniapp 继续只读查询，不写扫码事实；PDA 是现场扫码事实的唯一入口。

**收益假设**

连续 100 包扫码的成功输入焦点保持率 100%；暂存事实 UUID/正文保持率 100%；网络恢复后无冲突事实最终回传率 100%；冲突事实可见率 100%。测量方式：Android 仪器测试模拟连续键盘输入、断网/恢复、单条 409 冲突并核验 Room 与服务端事实；当前实测只覆盖持久队列和成功同步，分状态可见性及实体扫码枪体验待实测。

**风险与回退**

自动同步不能把冻结、确认或库存写入带进 PDA；只允许上传扫码事实。遇到冲突不得自动重编号、改重量或删除；若新状态面板异常，回退到当前“扫码记录/补传”入口，Room 中事实保持不变。

### O-05 小程序详情返回保留查询上下文

**现状与证据**

小程序定位是只读查询，列表支持关键词和分页：[outbound/index.js（4–30 行）](../apps/miniapp/pages/outbound/index.js#L4)。进入详情后返回会触发 `onShow` 并重置加载第一页，虽然关键词保留，但已滚动位置/后续页需要重新加载：[outbound/index.js（5–7、39–40 行）](../apps/miniapp/pages/outbound/index.js#L5)、[detail/index.js（5–8 行）](../apps/miniapp/pages/detail/index.js#L5)。

**方案 A 与方案 B**

- 方案 A（推荐）：从详情返回时保留关键词、页码、已加载记录和滚动位置；后台刷新当前页数据，列表变化时不清空用户上下文。优点是查下一张单不必重新滚动或翻页。
- 方案 B：每次返回都重新从第一页查询。优点是页面状态始终新鲜；缺点是长列表重复定位，现场单手操作增加滚动步骤。

推荐 A。小程序维持只读查询；扫码、盘点录入和任何库存写入仍不放到小程序。

**收益假设**

从详情返回到同一列表位置目标 1 次返回动作，不重新输入关键词，列表位置恢复率 100%。测量方式：微信开发者工具测试第 3 页打开详情并返回，记录输入动作、恢复页码和滚动锚点；当前返回状态基线待实测。

**风险与回退**

缓存可能短暂展示过期状态；返回时静默刷新当前页并标示刷新失败，保留本地结果与重试入口。若状态恢复引入页面生命周期问题，回退为当前从第一页刷新，不影响只读权限。

## 新增候选

### N-01 库存预警与库龄联动看板

**现状与证据**

旧系统已有库存预警字段和库龄报表入口：[StockList.vue（140、1023–1055 行）](D:/wms-new/wms-frontend-pure/src/views/wms/StockList.vue#L140)、[StockAging.vue](D:/wms-new/wms-frontend-pure/src/views/wms/report/StockAging.vue)；当前原型只有基础库存表：[stock.tsx（18–28 行）](../apps/web/src/features/outbound/stock.tsx#L18)。样本库存 122 行，适合先做服务端聚合。

**方案 A 与方案 B**

- 方案 A（推荐）：库存首页显示低于阈值和超过库龄分段的数量，点击直接带筛选进入库存列表；只读，不自动改库存。
- 方案 B：定时发送消息/短信。优点是不用打开系统；缺点是单用户场景增加通知配置和外部依赖，误报难撤回。

建议 A，先经用户批准；它解决“靠人盯表”，但不改变库存事实。

**收益假设**

从首页到异常库存目标 ≤2 步，预警漏报 0；计算 p95 <1s。测量方式：用 122 行样本和扩展 10k 行数据对账阈值/库龄 SQL；通知方案不做。

**风险与回退**

库龄起算口径未完全验证，初版必须显示截止日和计算规则；发现口径冲突时关闭看板入口，库存列表不受影响。

### N-02 批量导入与校验报告

**现状与证据**

sku.txt 已有 9018 行、141 个规格、无缺列/重复条码/非数字重量：[sku-analysis.json](../.local/prod-sample/sku-analysis.json)；旧 ERP 入库表单仍逐行添加明细：[InboundOrderForm.vue（466–560 行）](D:/wms-new/wms-frontend-pure/src/views/wms/InboundOrderForm.vue#L466)。当前原型 ProFormList 也逐行录入：[inbound/editor.tsx（98–124 行）](../apps/web/src/features/inbound/editor.tsx#L98)。

**方案 A 与方案 B**

- 方案 A（推荐）：允许粘贴条码或 CSV，服务端逐行校验条码、商品来源、重量精度，返回“可导入/错误行/重复行”报告；导入前只生成草稿，不直接改库存。
- 方案 B：前端直接解析并批量提交。优点是体验快；缺点是大文件、编码和规则校验容易绕过服务端。

建议 A，先经用户批准。该能力仅用于目录/事实辅助，不改变入库不扫码的业务边界，也不生成入库单明细或替代包数与总吨数独立登记。

**收益假设**

9018 条目录校验一次完成，目标报告在 10 秒内返回，错误行 100% 可定位；人工逐行录入不再作为规模化路径。测量方式：用 sku.txt 做全量回归，记录解析耗时、错误行数和重量一致性；当前基线已为 9018/9018 命中，耗时待实测。

**风险与回退**

错误文件只生成报告，不写库存；导入任务保存原文件摘要和校验版本。异常时回退到手工 ProForm，不删除草稿。

**风险说明：**若误接入入库建单生成包级记录，会把辅助条码数据误记为入库事实；导入入口和 API 必须限制为目录/事实辅助，不能扫码称重、生成入库明细或改变“入库不扫码”的边界。

## 删减

### D-01 隐藏低价值字段，保留数据库历史

**现状与证据**

真实样本中入库 `container_no` 仅 1/115、`delivery_no` 3/115、`remark` 1/115；出库 `container_no` 9/415、`remark` 1/415；入/出库明细 `detail_remark` 分别 0/182、0/544。字段仍存在于 CSV schema，应保留历史，不应强迫每次录入。

**方案 A 与方案 B**

- 方案 A（推荐）：首屏隐藏明细备注、柜号、来货单号等低频字段，放入“更多信息”折叠区；数据库、导出和详情仍可显示历史值。
- 方案 B：彻底删除字段和迁移数据。优点是界面更干净；缺点是破坏历史单据和旧接口兼容，不可逆。

推荐 A，属于可逆的界面减法。

**收益假设**

新建表单首屏字段减少 3–4 个，目标滚动/填写步骤减少 20%，空字段提交率下降；通过 Playwright 比较字段焦点序列，实际时长待实测。

**风险与回退**

用户可能需要偶尔填写柜号/合同号；折叠区保留并可通过详情查看。若业务确认某字段变为必填，只需恢复 UI，不需数据库迁移。

### D-02 不做无价值的企业化页面和流程

**现状与证据**

旧手册包含用户、角色、菜单权限和公告等页面，但 AGENTS 明确单用户、不做复杂 RBAC/多级审批；旧页面目录仍有 `UserList.vue`、`RoleList.vue`、`MessageCenter.vue`。当前系统只有 owner 身份和 channel 边界。

**方案 A 与方案 B**

- 方案 A（推荐）：权限页面记 N/A；保留登录、会话失效、操作日志、备份恢复和客户端边界。消息中心仅保留与单据/库存相关通知。
- 方案 B：照搬旧管理员/审核员/操作员和公告中心。优点是表面功能完整；缺点是增加配置、测试和误授权面，不解决单用户痛点。

推荐 A；只有出现第二个实际使用者才重新评估。

**收益假设**

菜单项减少但业务入口不减少；权限配置和审批点击目标为 0，登录和写入边界 E2E 通过。测量方式：检查路由数、无效菜单点击数和 channel 越权测试；当前基线待实测。

**风险与回退**

未来新增使用者会需要授权模型；在该触发条件出现前不实现。若需求改变，新增授权作为独立架构项目，不把临时角色塞进单用户模型。

## 组合与排序

排序按“业务价值 ÷ 成本 ÷ 风险”判断：

1. **B1a 数据正确性，必须与对应 P 同批**：U-02 单号、U-03 重量/确认分层、U-04 原值回退、库存/扫码目录用途隔离、库存调整事务。它们会改变库存或单据事实，须先以接口/E2E 验收。
2. **B1b 共同能力，可独立于 B1a 回滚**：U-01 基础查询壳、O-01 基础响应式/固定列、O-02 导出/打印 schema。它们复用层次高，但不应与库存正确性改动绑成一个提交。
3. **B2，核心 P 后紧接**：撤销审核/作废/更正（补偿事务与下游依赖校验）、O-03 键盘/恢复、O-04 PDA 连续扫码/补传反馈、O-05 小程序查询上下文、U-05 备份恢复验证、日志查询、库存查询增强和主数据完整字段。
4. **B3，后置**：盘点、四类报表、消息中心、系统配置、N-01/N-02。它们依赖数据口径、模型或候选批准，适合独立交付。

P0 收敛标准：只保留会改变库存/单据可追溯性、阻断旧 ERP 核心路径，或被两个以上模块依赖的能力；权限因单用户约束为 N/A。

## 现在最值得做但不该做

- **不做多用户/RBAC/多级审批**：单用户没有收益，反而扩大会话、菜单和测试面；除非出现第二个实际使用者并放开约束。
- **不做 PDA 直接扣库存或差异放行**：会突破“PDA 只写事实、Web 明确确认”的边界，库存错误不可接受。
- **不做模糊商品映射和跨来源经营总数**：141 SPEC 与 428 ERP 商品没有可靠键，错误合并比缺少汇总更危险。
- **不做实时消息/短信/外部 ERP 对接**：当前没有稳定接口契约和通知受众，先做可解释的只读预警看板。
- **不做彻底删除低频历史字段**：界面减法可逆，数据迁移删除不可逆且没有收益证据。
