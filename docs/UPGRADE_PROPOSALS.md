# 升级与重构提案

本轮只产出提案和文档，不改业务代码。提案依据旧 ERP 页面/控制器、当前原型、真实样本统计和现有 E2E；提案中的目标值是验收指标，不代表已经实现。

## 升级

### U-01 统一查询壳与服务端筛选

**现状与证据**

旧 ERP 的入库单列表已经有筛选抽屉、批量操作和导出，但入口与列表状态分散：`D:\wms-new\wms-frontend-pure\src\views\wms\InboundOrderList.vue:634-678,790-981`；出库列表同样重复一套筛选和批量逻辑：`D:\wms-new\wms-frontend-pure\src\views\wms\OutboundOrderList.vue:643-691,799-981`。当前原型入库和出库列表都显式 `search={false}`，只保留单号关键词/状态：`apps/web/src/features/inbound/list.tsx:44-69`、`apps/web/src/features/outbound/list.tsx:61-108`。

**方案 A 与方案 B**

- 方案 A（推荐）：做一个 ProTable 列表壳，筛选条件统一为日期范围、状态、仓库、往来单位、单号；条件通过 API 下推，列显隐和筛选保存在 localStorage。优点是重复代码少、万级数据可控；成本是需要统一接口参数。
- 方案 B：保留每页独立列表，只增加搜索字段。优点是初期改动小；缺点是筛选语义和空/错态会继续漂移，后续导出要重复维护。

推荐 A，因为它直接解决当前两个列表的重复实现，并且是导出、报表和日志查询的共同基础。

**收益假设**

旧系统“打开列表→打开筛选→填条件→查询”至少 4 个动作，新方案目标为首屏填完条件后 2 个动作完成查询；10,000 行数据翻页 p95 <500ms，首屏 p95 <1.5s。测量方式：Playwright 记录点击/键盘动作；脚本向本地 MySQL 生成 10,000 行临时数据并记录 API p50/p95；当前原型基线为 1 个关键词 + 1 个状态控件，完整多条件时延待实测。

**风险与回退**

查询参数错映射会返回错误集合；通过接口契约测试逐个字段核对，发现问题时回退到原查询端点。localStorage 结构带版本号，升级失败清除该页筛选而不影响数据。

### U-02 RK/CK 自动单号与草稿键盘流

**现状与证据**

旧 ERP 已有编号生成器：`D:\wms-new\wms-backend\utils\bill_no.js:11-71`；但当前原型仍要求手填入库号和出库号：`apps/web/src/features/inbound/editor.tsx:80`、`apps/web/src/features/outbound/editor.tsx:105`。现有 E2E 也必须手填 `IN-E2E...` 和 `OUT-E2E...`：`tests/e2e/outbound.spec.ts:80,108`。

**方案 A 与方案 B**

- 方案 A（推荐）：服务端事务生成 `RK-YYYYMMDD-####` 和 `CK-YYYYMMDD-####`，创建草稿即取得号，表单显示只读预览；`Ctrl+S` 保存、`Esc` 返回，保存失败保留草稿。优点是唯一性和回溯最强。
- 方案 B：前端按日期计算预览，提交时服务端再生成。优点是接口改动小；缺点是预览与最终号可能不一致，用户仍需重新核对。

推荐 A；业务已决定入库/出库使用独立前缀，不能继续沿用手填。

**收益假设**

建单少 1 个手填字段，目标新建入库/出库均不超过 2 屏；同一日期并发取号唯一率 100%，重复号 0。测量方式：E2E 并发创建 50 个草稿检查唯一性；键盘任务记录按键数和完成时长；当前基线是两个表单各 1 次手填，时长待实测。

**风险与回退**

序列写入失败可能留下空号；空号允许但不可复用，事务失败不写业务单。若规则迁移出现问题，配置开关回到手填只读历史号，服务端仍拒绝重复号。

### U-03 入库重量校验与出库事实确认分层

**现状与证据**

样本重量范围 60–389.5kg，9018/9018 条码重量一致，说明统一件重反算不成立：`.local/prod-sample/sku-analysis.json`。当前入库表单已分别录包数和总吨数：`apps/web/src/features/inbound/editor.tsx:112-123`，但没有汇总差异提示。旧 ERP 入库审核会在同一动作中更新库存：`D:\wms-new\wms-backend\controllers\inbound_order.js:456-545`；当前出库则已把 PDA 事实与 Web 确认拆开：`apps/api/src/features/outbound/confirm.ts:25-36`。

**方案 A 与方案 B**

- 方案 A（推荐）：入库在同一表单即时显示包数/吨数合计和字段级错误；出库详情保留“扫码事实→冻结→Web 确认”三段，并在确认抽屉显示包级实重、库存前后值。优点是既不丢重量事实，又能防误扣。
- 方案 B：只在提交后由后端返回汇总错误，详情仍沿用一个审核按钮。优点是开发快；缺点是错误发现晚，且审核语义继续混杂。

推荐 A，因为它保留现有库存事务/幂等语义，并把错误前移到录入现场。

**收益假设**

目标是重量/包数不一致时 0 次静默提交，重复确认 0 次重复扣减；出库确认前核对由跨页查找降为详情 1 屏。测量方式：E2E 构造 10 个重量差异和 3 次重复确认；比对库存、流水和审计；当前原型已覆盖重复确认幂等，差异提示耗时待实测。

**风险与回退**

汇总校验过严会阻断历史异常单；对历史数据只警示不阻断，对新单按配置启用硬校验。确认抽屉异常时事务回滚，保留 PDA 原事实，回退到旧确认按钮只允许在 feature flag 下用于测试。

### U-04 未知状态/流水类型原文回退与来源标签

**现状与证据**

样本中单据状态为 `audited` 114/115（入库）、`audited` 414/415（出库）；流水类型为 `check` 47、`import` 60、`inbound` 182、`outbound` 539，且有 24 条软删：`.local/prod-sample/*.csv` 聚合统计。当前 Web 仅在出库状态组件中做部分映射：`apps/web/src/features/outbound/status.tsx:3-9`。

**方案 A 与方案 B**

- 方案 A（推荐）：保留数据库原字符串，展示层统一 `StatusTag`/`JournalTypeTag`，已知值显示中文，未知值显示原文并带“来源值”提示；库存/报表常驻来源标签。
- 方案 B：导入时把未知值映射到有限枚举。优点是页面更简单；缺点是历史语义不可逆，审计和报表会失真。

推荐 A，符合真实数据保留原值的决定。

**收益假设**

目标页面状态空白数 0、未知值报错数 0；用户无需回到数据库确认原值。测量方式：E2E 注入 `future_status`/`future_type` fixture，遍历列表、详情、流水和报表；当前基线只覆盖已知出库标签，未知值覆盖率待实测。

**风险与回退**

标签文案错误不会改变数据，但可能误导用户；未知值使用中性灰和原文，不猜中文含义。若新标签组件异常，回退为纯原文字段显示。

## 优化

### O-01 列表信息密度、响应式和固定列

**现状与证据**

当前出库表已有固定状态/操作列和列显隐持久化：`apps/web/src/features/outbound/list.tsx:21-34,76-77`，但入库表没有固定操作列且两个列表通过 `scroll.x` 硬撑：`apps/web/src/features/inbound/list.tsx:44-52`。旧 StockList 同时放置库存重建、重置和清零等高风险按钮：`D:\wms-new\wms-frontend-pure\src\views\wms\StockList.vue:777-816`。

**方案 A 与方案 B**

- 方案 A（推荐）：1440/1280 使用关键列左固定、操作列右固定，次要列进入列设置；1280 以下筛选折叠为抽屉，表格保持页面无横向滚动，危险库存操作移入明确原因抽屉。
- 方案 B：所有列保留，依赖横向滚动。优点是信息一次展示；缺点是关键字段和操作会离开视口，现场误操作概率更高。

推荐 A，符合 ProTable 和现有响应式约束。

**收益假设**

200 行列表仍能扫读关键列，主要操作在首屏可见；1280/1440 页面级横向滚动 0。测量方式：Playwright 两个 viewport 断言 `scrollWidth <= innerWidth`，记录首屏操作可见性；当前 1280 E2E 已有布局断言，列固定策略待实测。

**风险与回退**

固定列宽设置过大可能压缩内容；为列设置定义最小/最大宽度并允许用户恢复默认。响应式折叠异常时回退为桌面布局，不改变数据接口。

### O-02 页面、导出、打印共用字段定义

**现状与证据**

旧 ERP 列表导出和详情导出分开实现：入库列表 `D:\wms-new\wms-frontend-pure\src\views\wms\InboundOrderList.vue:444-537`、入库详情 `InboundOrderDetail.vue:107-148`；出库同样有列表/详情两套导出。当前原型没有导出和打印组件。

**方案 A 与方案 B**

- 方案 A（推荐）：为每个业务列表定义一份字段 schema，ProTable、CSV/Excel、打印模板都从 schema 生成；CSV 使用 UTF-8 BOM，Excel/打印保留同一列顺序和合计。
- 方案 B：页面、导出、打印各写一份字段映射。优点是局部灵活；缺点是字段变更容易漏改，出现屏幕与打印不一致。

推荐 A，减少长期维护成本。

**收益假设**

同一单据屏幕/导出/打印字段差异 0；筛选到导出 ≤3 步，10,000 行分页导出不占满浏览器内存。测量方式：脚本比较字段 schema、导出表头和打印 DOM；导出大数据时记录内存与耗时；均待实测。

**风险与回退**

历史字段缺失时显示空值并保留列，不改变历史记录；schema 生成器出错时可下载原始 CSV，打印仍可用基础模板。

### O-03 输入恢复与键盘路径

**现状与证据**

旧入/出库表单将表头、客户/供应商、车辆、明细拆在长页面：`D:\wms-new\wms-frontend-pure\src\views\wms\InboundOrderForm.vue:354-560`、`OutboundOrderForm.vue:427-749`。当前 ProForm 已有字段级规则，但错误只通过 Alert 展示：`apps/web/src/features/inbound/editor.tsx:64-65`、`apps/web/src/features/outbound/editor.tsx:88`。

**方案 A 与方案 B**

- 方案 A（推荐）：表单按“单据头/明细/合计”分组，回车跳到下一字段，Ctrl+S 保存，Esc 返回；失败时保留表单值并滚动到第一个错误。
- 方案 B：继续使用默认 ProForm 提交，只增加错误 toast。优点是改动小；缺点是现场录入需要鼠标找错，网络失败容易重复提交。

推荐 A，键盘流只影响前端交互，回退容易。

**收益假设**

目标新建/编辑 ≤2 屏，错误定位 1 次跳转，网络失败不丢字段；常规录入按键/点击数减少 30%，待实测。测量方式：Playwright keyboard-only 用例和故障注入，记录操作事件数与表单值保持率。

**风险与回退**

快捷键可能与浏览器冲突，输入框内只在无组合输入时生效；快捷键异常可关闭 feature flag，保留鼠标操作。

## 新增候选

### N-01 库存预警与库龄联动看板

**现状与证据**

旧系统已有库存预警字段和库龄报表入口：`D:\wms-new\wms-frontend-pure\src\views\wms\StockList.vue:140,1023-1055`、`D:\wms-new\wms-frontend-pure\src\views\wms\report\StockAging.vue`；当前原型只有基础库存表：`apps/web/src/features/outbound/stock.tsx:18-28`。样本库存 122 行，适合先做服务端聚合。

**方案 A 与方案 B**

- 方案 A（推荐）：库存首页显示低于阈值和超过库龄分段的数量，点击直接带筛选进入库存列表；只读，不自动改库存。
- 方案 B：定时发送消息/短信。优点是不用打开系统；缺点是单用户场景增加通知配置和外部依赖，误报难撤回。

建议 A，先经用户批准；它解决“靠人盯表”，但不改变库存事实。

**收益假设**

从首页到异常库存目标 ≤2 步，预警漏报 0；计算 p95 <1s。测量方式：用 122 行样本和扩展 10k 行数据对账阈值/库龄 SQL；通知方案不做。

**风险与回退**

库龄起算口径未完全验证，初版必须显示截止日和计算规则；发现口径冲突时关闭看板入口，库存列表不受影响。

### N-02 批量导入与校验报告

**现状与证据**

sku.txt 已有 9018 行、141 个规格、无缺列/重复条码/非数字重量：`.local/prod-sample/sku-analysis.json`；旧 ERP 入库表单仍逐行添加明细：`D:\wms-new\wms-frontend-pure\src\views\wms\InboundOrderForm.vue:466-560`。当前原型 ProFormList 也逐行录入：`apps/web/src/features/inbound/editor.tsx:98-124`。

**方案 A 与方案 B**

- 方案 A（推荐）：允许粘贴条码或 CSV，服务端逐行校验条码、商品来源、重量精度，返回“可导入/错误行/重复行”报告；导入前只生成草稿，不直接改库存。
- 方案 B：前端直接解析并批量提交。优点是体验快；缺点是大文件、编码和规则校验容易绕过服务端。

建议 A，先经用户批准；它适合 9018 条目录和后续批量入库，但必须继续遵守入库不扫码的业务边界，条码导入只用于目录/事实辅助场景。

**收益假设**

9018 条目录校验一次完成，目标报告在 10 秒内返回，错误行 100% 可定位；人工逐行录入不再作为规模化路径。测量方式：用 sku.txt 做全量回归，记录解析耗时、错误行数和重量一致性；当前基线已为 9018/9018 命中，耗时待实测。

**风险与回退**

错误文件只生成报告，不写库存；导入任务保存原文件摘要和校验版本。异常时回退到手工 ProForm，不删除草稿。

## 删减

### D-01 隐藏低价值字段，保留数据库历史

**现状与证据**

真实样本中入库 `container_no` 仅 1/115、`delivery_no` 3/115、`remark` 1/115；出库 `container_no` 9/415、`remark` 1/415；入/出库明细 `detail_remark` 分别 0/182、0/544。字段仍存在于 CSV schema，应保留历史，不应强迫每次录入。

**方案 A 与方案 B**

- 方案 A（推荐）：首屏隐藏明细备注、柜号、来货单号等低频字段，放入“更多信息”折叠区；数据库、导出和详情仍可显示历史值。
- 方案 B：彻底删除字段和迁移数据。优点是界面更干净；缺点是破坏历史单据和旧接口兼容，不可逆。

推荐 A，属于可逆的界面减法。

**收益假设**

新建表单首屏字段减少 3–4 个，目标滚动/填写步骤减少 20%，空字段提交率下降；通过 Playwright 比较字段焦点序列，实际时长待实测。

**风险与回退**

用户可能需要偶尔填写柜号/合同号；折叠区保留并可通过详情查看。若业务确认某字段变为必填，只需恢复 UI，不需数据库迁移。

### D-02 不做无价值的企业化页面和流程

**现状与证据**

旧手册包含用户、角色、菜单权限和公告等页面，但 AGENTS 明确单用户、不做复杂 RBAC/多级审批；旧页面目录仍有 `UserList.vue`、`RoleList.vue`、`MessageCenter.vue`。当前系统只有 owner 身份和 channel 边界。

**方案 A 与方案 B**

- 方案 A（推荐）：权限页面记 N/A；保留登录、会话失效、操作日志、备份恢复和客户端边界。消息中心仅保留与单据/库存相关通知。
- 方案 B：照搬旧管理员/审核员/操作员和公告中心。优点是表面功能完整；缺点是增加配置、测试和误授权面，不解决单用户痛点。

推荐 A；只有出现第二个实际使用者才重新评估。

**收益假设**

菜单项减少但业务入口不减少；权限配置和审批点击目标为 0，登录和写入边界 E2E 通过。测量方式：检查路由数、无效菜单点击数和 channel 越权测试；当前基线待实测。

**风险与回退**

未来新增使用者会需要授权模型；在该触发条件出现前不实现。若需求改变，新增授权作为独立架构项目，不把临时角色塞进单用户模型。

## 组合与排序

排序按“业务价值 ÷ 成本 ÷ 风险”判断：

1. **B1，必须与 P 同批**：U-02 单号、U-03 重量/确认分层、U-04 原值回退、O-01 基础响应式、O-02 导出/打印字段 schema、库存调整和双来源口径。它们直接影响库存正确性、追溯或所有后续页面的共同能力。
2. **B2，P 完成后紧接**：U-01 统一查询壳、O-03 键盘/恢复、日志查询、库存查询增强、主数据完整字段。它们主要减少日常操作成本，失败可局部回退。
3. **B3，后置**：盘点、四类报表、消息中心、系统配置、N-01/N-02。它们价值明确但依赖口径、数据模型或用户确认，适合独立批次。

P0 收敛标准：只保留会改变库存/单据可追溯性、阻断旧 ERP 核心路径，或被两个以上模块依赖的能力；权限因单用户约束为 N/A。

## 现在最值得做但不该做

- **不做多用户/RBAC/多级审批**：单用户没有收益，反而扩大会话、菜单和测试面；除非出现第二个实际使用者并放开约束。
- **不做 PDA 直接扣库存或差异放行**：会突破“PDA 只写事实、Web 明确确认”的边界，库存错误不可接受。
- **不做模糊商品映射和跨来源经营总数**：141 SPEC 与 428 ERP 商品没有可靠键，错误合并比缺少汇总更危险。
- **不做实时消息/短信/外部 ERP 对接**：当前没有稳定接口契约和通知受众，先做可解释的只读预警看板。
- **不做彻底删除低频历史字段**：界面减法可逆，数据迁移删除不可逆且没有收益证据。
