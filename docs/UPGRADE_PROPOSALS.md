# 升级与重构提案

本轮只产出提案和文档，不改业务代码。提案依据旧 ERP 页面/控制器、当前原型、真实样本统计和现有 E2E；提案中的目标值是验收指标，不代表已经实现。所有代码证据均复核到文件现有行范围，并提供可点击行链接；新提案目标需实测，不以设计稿代替验收。

## 升级

### U-01 统一查询壳与服务端筛选

**现状与证据**

旧 ERP 的入库单列表已经有筛选抽屉、批量操作和导出，但入口与列表状态分散：[InboundOrderList.vue（634–678、790–981 行）](D:/wms-new/wms-frontend-pure/src/views/wms/InboundOrderList.vue#L634)；出库列表同样重复一套筛选和批量逻辑：[OutboundOrderList.vue（643–691、799–981 行）](D:/wms-new/wms-frontend-pure/src/views/wms/OutboundOrderList.vue#L643)。当前原型入库和出库列表都显式 `search={false}`，只保留单号关键词/状态：[inbound/list.tsx（44–69 行）](../apps/web/src/features/inbound/list.tsx#L44)、[outbound/list.tsx（61–108 行）](../apps/web/src/features/outbound/list.tsx#L61)。

**方案 A 与方案 B**

- 方案 A（推荐）：做一个 ProTable 列表壳，筛选条件统一为日期范围、状态、仓库、往来单位、单号；条件通过 API 下推，列显隐和筛选保存在 localStorage。优点是重复代码少、万级数据可控；成本是需要统一接口参数。
- 方案 B：保留每页独立列表，只增加搜索字段。优点是初期改动小；缺点是筛选语义和空/错态会继续漂移，后续导出要重复维护。

推荐 A，因为它直接解决当前两个列表的重复实现，并且是导出、报表和日志查询的共同基础。

**收益假设**

旧系统“打开列表→打开筛选→填条件→查询”至少 4 个动作，新方案目标为首屏填完条件后 2 个动作完成查询；10,000 行数据翻页 p95 <500ms，首屏 p95 <1.5s。测量方式：Playwright 记录点击/键盘动作；脚本向本地 MySQL 生成 10,000 行临时数据并记录 API p50/p95；当前原型基线为 1 个关键词 + 1 个状态控件，完整多条件时延待实测。

**风险与回退**

查询参数错映射会返回错误集合；通过接口契约测试逐个字段核对，发现问题时回退到原查询端点。localStorage 结构带版本号，升级失败清除该页筛选而不影响数据。

### U-02 RK/CK 自动单号与草稿键盘流

**现状与证据**

旧 ERP 已有编号生成器：[bill_no.js:11](D:/wms-new/wms-backend/utils/bill_no.js#L11)。提案基线中两个表单各需手填一次；B1a 第 1 提交已改为服务端取号：[inbound/editor.tsx:80](../apps/web/src/features/inbound/editor.tsx#L80)、[outbound/editor.tsx:105](../apps/web/src/features/outbound/editor.tsx#L105)。现行 E2E 验证自动号与编辑保号：[outbound.spec.ts:76](../tests/e2e/outbound.spec.ts#L76)。

**方案 A 与方案 B**

- 方案 A（推荐）：服务端事务生成 `RK-YYYYMMDD-####` 和 `CK-YYYYMMDD-####`，与业务单/幂等结果一起提交；配置页提供服务端非占号预览，最终号以创建成功响应为准。草稿、`Ctrl+S`、`Esc` 留后续批次，不纳入本提交。
- 方案 B：前端自行按日期计算预览。成本较低，但不了解历史占号和服务器业务日，不能作为权威取号；两方案均不承诺并发下预览等于最终号。

推荐 A；业务已决定入库/出库使用独立前缀，不能继续沿用手填。

**收益假设**

建单各少 1 个手填字段。实测两类各 50 个并发 HTTP 创建，唯一率 100%，重复号 0：[numbering-concurrency.test.ts](../apps/api/tests/numbering-concurrency.test.ts)。两屏/键盘时长仍待实测，不把当前创建称为草稿。

**风险与回退**

首次按完整格式的历史最大序号初始化（含软删、不同补零宽度）；不能解析的历史号保留。每次候选号再精确查两类单据，冲突立即报错，不循环猜号。修改宽度只改补零，保存前碰撞/容量校验；事务失败同时回滚计数器，未提交的号未被消耗。旧客户端原号兼容且响应标记弃用，不静默换号。回退须同时回退 Web/API；非空 004 表保留，不执行 down，不承诺不存在的配置开关。

### U-03 入库重量校验与出库事实确认分层

**现状与证据**

样本重量范围 60–389.5kg，9018/9018 条码重量一致，说明统一件重反算不成立：[sku-analysis.json](../.local/prod-sample/sku-analysis.json)。当前入库表单已分别录包数和总吨数：[inbound/editor.tsx（112–123 行）](../apps/web/src/features/inbound/editor.tsx#L112)，但没有汇总差异提示。旧 ERP 入库审核会在同一动作中更新库存：[inbound_order.js（456–545 行）](D:/wms-new/wms-backend/controllers/inbound_order.js#L456)；当前出库则已把 PDA 事实与 Web 确认拆开：[confirm.ts（25–36 行）](../apps/api/src/features/outbound/confirm.ts#L25)。

**方案 A 与方案 B**

- 方案 A（推荐）：入库在同一表单即时显示包数/吨数合计和字段级错误；出库详情保留“扫码事实→冻结→Web 确认”三段，并在确认抽屉显示包级实重、库存前后值。优点是既不丢重量事实，又能防误扣。
- 方案 B：只在提交后由后端返回汇总错误，详情仍沿用一个审核按钮。优点是开发快；缺点是错误发现晚，且审核语义继续混杂。

推荐 A，因为它保留现有库存事务/幂等语义，并把错误前移到录入现场。

归属已定：入库审核/明确确认是正向库存边界，放 **B1a 第 3 提交**；撤销审核、作废、更正放 **B2**，需补偿流水及后续出库依赖校验，不可只改状态或删原流水。**B1b 不承接业务状态机**。第 1 提交维持现有登记即确认行为，不宣称审核已补齐。

**收益假设**

目标是重量/包数不一致时 0 次静默提交，重复确认 0 次重复扣减；出库确认前核对由跨页查找降为详情 1 屏。测量方式：E2E 构造 10 个重量差异和 3 次重复确认；比对库存、流水和审计；当前原型已覆盖重复确认幂等，差异提示耗时待实测。

**风险与回退**

汇总校验过严会阻断历史异常单；对历史数据只警示不阻断，对新单按配置启用硬校验。确认抽屉异常时事务回滚，保留 PDA 原事实，回退到旧确认按钮只允许在 feature flag 下用于测试。

### U-04 未知状态/流水类型原文回退与用途隔离

**现状与证据**

样本中单据状态为 `audited` 114/115（入库）、`audited` 414/415（出库）；流水类型为 `check` 47、`import` 60、`inbound` 182、`outbound` 539，且有 24 条软删：[prod-sample CSV 汇总](../.local/prod-sample/manifest.json)。基线只有出库部分映射；B1a 第 1 提交改为共享 [StatusTag](../apps/web/src/components/StatusTag/index.tsx#L1) 与 [JournalTypeTag](../apps/web/src/components/JournalTypeTag/index.tsx#L1)。

**方案 A 与方案 B**

- 方案 A（采用）：保留数据库原字符串，统一 `StatusTag`/`JournalTypeTag`；未知状态用“状态待识别：原文”灰色标签，详情常驻说明未知含义、核对原单的方法及出库确认禁用。库存业务前提已纠正为用途隔离：库存与单据只认 erp-product，固定 ERP 视图；sku-spec 只属于 B1c 条码目录页面，未归属仅诊断日志，无库存入口或占位。保留 API 来源参数守卫和严格契约；报表尚未实现，后续只统计 ERP。
- 方案 B：导入时把未知值映射到有限枚举。优点是页面更简单；缺点是历史语义不可逆，审计和报表会失真。

推荐 A，符合真实数据保留原值的决定。

**收益假设**

目标页面状态空白数 0、未知值报错数 0；用户无需回到数据库确认原值。测量方式：E2E 注入 `future_status`/`future_type` fixture，遍历列表、详情、流水和报表；当前基线只覆盖已知出库标签，未知值覆盖率待实测。

**风险与回退**

标签文案错误不会改变数据，但可能误导用户；未知值保留原文，不猜中文含义，关键说明不藏在 tooltip 中。第 2 批无需数据迁移，应用代码可回退；旧 `/stock` 数组保持兼容。SPEC 是扫码目录而非库存；验收固定 ERP 视图、无目录库存入口/请求/占位。原非 ERP 测试数据仅作异常夹具验证守卫，不代表业务库存。

### U-05 备份产物校验与恢复演练

**现状与证据**

当前备份脚本检查本地数据库身份并生成 SQL 文件，但没有产物摘要/大小清单或完成后校验：[backup.ts（7–29 行）](../scripts/backup.ts#L7)。恢复脚本会恢复到新库、校验库身份并在失败时清理本次新库，但没有校验和检查或数据级完整性对账：[restore.ts（7–28 行）](../scripts/restore.ts#L7)。操作日志由审计函数写入事务：[audit.ts（6–10 行）](../apps/api/src/shared/audit.ts#L6)。

**方案 A 与方案 B**

- 方案 A（推荐）：备份完成后写 SHA-256、文件大小、数据库身份和时间 manifest；恢复前校验摘要，导入新库后运行表行数、关键重量汇总和身份检查；通过后仍由人显式切换，失败只清理本次隔离恢复库。
- 方案 B：只定期人工运行 `npm run restore`，人工抽查若干页面。优点是实现成本低；缺点是无法发现备份截断或样本之外的数据缺失，恢复结果依赖操作者记忆。

推荐 A。它验证“能恢复且内容一致”，不改变当前库、不连接生产，也不把审计日志当审批流程。

**收益假设**

每个备份产物都有可验证摘要的比例 100%；每次恢复演练执行行数/重量对账；损坏文件在导入前拒绝；隔离恢复库端到端恢复目标 <15 分钟，当前恢复时长待实测。测量方式：对 SQL 文件做单字节篡改、执行本地恢复演练并核对 manifest、指定表计数与总重量；每次迁移验收前至少跑一次。

**风险与回退**

摘要只能证明文件未变化，不能单独证明数据逻辑完整，因此恢复后仍须跑数据对账。校验/导入失败只删除本次随机命名的恢复库，原开发库和备份文件保留；如果自动核对脚本有误，可回退到人工只读对账，不自动切换数据库。

### U-06 条码目录版本化与上传（P；B1c-1 已落地，B1c-2 待实施）

**现状与证据**

旧 PDA 已有 SKU 管理，不是新增能力：本地版本/条数/来源见 [V10SkuActivity.kt:159–185](D:/wms-new/wms-pda/app/src/main/java/com/jinglun/wmspda/ui/V10SkuActivity.kt#L159)，文件导入见 [101–108、201–217](D:/wms-new/wms-pda/app/src/main/java/com/jinglun/wmspda/ui/V10SkuActivity.kt#L101)，云端更新见 [114–118、189–198](D:/wms-new/wms-pda/app/src/main/java/com/jinglun/wmspda/ui/V10SkuActivity.kt#L114)。保留“可导入、可查版本、可更新”的能力，按本次业务决定将权威发布入口集中到 Web，不照搬 USB 与云端争夺新旧的规则。

当前约 9018 条/141 规格是基线规模，不是每次上传的固定行数。每次 `sku.txt` 是当前有效条码全量快照；消失的条码按业务视为已出库，无逐条失效确认。**目录不作为库存/单据/报表的数据集，不自动扣库存、确认单据或回写历史**；包的实重只能作为扫码时形成的独立事实供后续出库核对。库存与单据的商品仍只认 `erp-product`。

现有模型不能直接覆盖目录后声称上述保证成立：

- [001_initial.up.sql:37–52](../apps/api/migrations/001_initial.up.sql#L37) 将目录按 barcode 单键覆盖、版本限定为 1，事实外键还指向该目录；[契约 index.ts:37–46、79–84](../packages/contracts/src/index.ts#L37) 也将目录版本写死为 1。
- [outbound/repository.ts:12–17](../apps/api/src/features/outbound/repository.ts#L12) 从当前目录取商品归属，[assemble.ts:14–22](../apps/api/src/features/outbound/assemble.ts#L14) 据此分配明细实扫量并生成摘要；删码/改规格可能使旧事实的明细归属丢失。冻结与确认依赖这份结果（[freeze.ts:14–18](../apps/api/src/features/scan/freeze.ts#L14)、[confirm.ts:27–35](../apps/api/src/features/outbound/confirm.ts#L27)）。
- PDA [ScanRepository.kt:14–20](../apps/pda/app/src/main/java/cn/maozhi/wms/pda/scan/ScanRepository.kt#L14) 也用当前缓存分配商品及累计旧事实；[ScanDao.kt:23–24](../apps/pda/app/src/main/java/cn/maozhi/wms/pda/data/ScanDao.kt#L23) 只按条码替换，没有整版切换，不能正确表达全量快照中的移除。

**方案 A 与方案 B**

以下是待实施设计，不是现有表、端点或迁移；只用本地隔离 MySQL 8 验证。推荐 **A：完整不可变版本 + 单一活动指针 + 不可变事实上下文**，不按整张出库单锁目录版本。

| 方案 A 表/实体 | 关键字段与约束（设计） | 用途 |
|---|---|---|
| `catalog_versions` | version_id 为单调分配的正整数主键（允许空号）；upload_uuid 唯一；base_version/revision；staging/validated/published 状态；原文件摘要、规范化内容摘要、解析规则版本、文件引用、行数/规格数、操作者与时间 | 同时记录上传任务和版本；校验完成后条目不可编辑，发布过的版本永久保留，是否当前版由 head 决定 |
| `catalog_entries` | 主键 `(version_id, barcode)`；规格原文、原始 kg 文本、精确 `weight_tonnes DECIMAL(12,4)`；版本外键 RESTRICT | 同一条码可存在于多版；活动版移除只是新版本不含该码，不删除旧行；不以 ERP 商品外键或 SPEC 编码猜归属 |
| `catalog_head` | 固定单行；active_version_id、revision；外键指向已校验版本 | 发布事务唯一切换点；目录读取只看当前指针或显式历史版本，绝不读取 staging |
| `scan_fact_context` | fact_id 唯一且外键 RESTRICT；catalog_version_id、barcode；当时规格/实重快照；outbound_line_id 外键 RESTRICT、ERP 商品编码快照；resolved_at（本机解析时间）、绑定来源 | PDA 离线随事实原子落盘，回传时服务端与事实同事务保存且重量一致、不可覆盖；关联历史 `(version_id, barcode)`；旧事实用附表扩展，原 UUID/正文/hash/实重不改 |

B1c-1 落地为原字节 MEDIUMBLOB 与候选同一事务保存，原文件 SHA/规范化 SHA 分开校验；发布只在 MySQL 内提交指针、版本状态、审计、幂等结果，不引入文件系统双写。文件与版本 manifest 纳入备份恢复，均不进入 Git；未发布残留不出现在业务查询里。上传/发布只允许现有 Web 身份和写入校验，PDA 只能读取/扫码，保留发布成功与失败诊断日志，不记录凭据。时间按现有 UTC `DATETIME(3)` 约定保存；外部重量继续整数克，换算不经过浮点舍入。目录 v1 的 SPEC 编码仅保留历史兼容，不随新增规格重新排序编号；新版条目直接保留规格原文，上传不创建/改写 ERP 商品或建立全局 SPEC→ERP 映射。

| 方案 B 表/实体 | 关键字段与约束（设计） | 取舍 |
|---|---|---|
| `catalog_revisions` + `catalog_current` | revision 元数据；current 按 barcode 单键保存当前规格/实重 | 当前查询直接，但必须在一个事务内应用全部差异，不能边上传边对外可见 |
| `catalog_entry_history` | `(barcode, from_version)`；to_version、规格/实重、removed 标记 | 保存改重、移除、重新出现的完整区间历史；区间重叠/缺口需额外校验，不能只留操作日志 |
| `scan_fact_context` | 同 A 的事实版本、实重、ERP 明细归属快照 | 不依赖 current 回查旧事实；历史恢复还需按 revision 重建目录 |

A 每版多存一份约 9k 条数据，但查历史、原子切换和恢复都直观，发布锁期短；B 节省未变条目存储，却增加差异算法、删除/再出现和区间重建风险。按需更新的当前规模优先选 A，不为节省这点空间引入 SCD 区间模型。两方案都不允许只覆盖当前目录、让旧事实随后跟着变。

上传流程（Web 单用户，无审批流）：

1. 选择全量 `sku.txt` → 服务端解析、持久化待发布版。保留原文件和行号，明确编码；无法无损解码时报错，不猜乱码。条码保留大小写/前导零，规格保留原文；缺列、非数字/非正重量、重复条码（即使重量相同）、超出现有重量契约上限或无法精确到 0.1kg 的值，均整版拒绝，不跳过错误行。60–389.5kg 只是样本分布，不是新文件合法范围。
2. 与当时 active version 比较，显示新/旧条数、规格数及新增/移除/规格变化/重量变化/不变；规格和重量同时变化的条码只计一次“变化”，筛选明细可分别显示两个变化。重量展示旧→新 kg 与四位吨数，不展示“库存损益”。
3. 移除文案为“本版移除（业务含义：已出库）；已扫记录保留，库存仅由 Web 确认链路处理”。不逐条确认、不设失效待办。可解析的零条快照允许发布，醒目显示“0 条有效码/本版移除全部”，仍只使用同一个发布动作；解析失败不能被当作空快照。
4. 点击一次“发布整版”。短事务锁 head，检查预览的 base revision 未变、候选 version_id 大于当前版且完整性已校验，再一次提交指针/版本状态/审计/幂等结果。并发发布已改变 base 时返回版本冲突；重算需建立后继待发布任务/版本并保留原任务结果，不能重用旧编号覆盖较新版。目录读取看到完整旧版或完整新版，没有中间态；PDA 在下次完整同步后才切换本地版。
5. 同 upload_uuid + 相同文件摘要重试只返回原任务/版本，不重复发布；同 UUID 不同正文拒绝。内容与任一完整历史版一致时显示“与第 N 版内容一致”，默认不增版；确需重建须页面二次确认并传 rebuildOfVersionId，服务端核对同内容，hash 不设全局唯一；恢复旧内容也生成后继版，活动版本号不倒退。事务提交前失败，活动版完全不动；提交后丢响应，按任务 ID 查结果，不盲目再次发布。

PDA 同步与新扫码（已定：本地同步版本 + 服务端接受历史版本事实）：

1. “最新版”定义为 **PDA 上次成功同步、完整下载并切换到本地的目录版本**，不是服务端此刻的活动版。PDA 常态为断网扫码，只有上传事实与刷新目录才回到有网处；服务端发布新版不会使设备尚未刷新的本地版失效，不以版本年龄或离线时长拒绝合法历史版本事实。
2. 每次扫码在本机 Room 事务中读取本地版本指针及该版条目，解析条码、取该版实重，将 UUID、原正文（planId、ERP 作业行 ID、barcode、catalogVersion、weightGrams、规格快照、设备/扫描时间等）与待回传状态原子落盘。落盘成功即为新的成功扫码事实，计入本机实扫量并提示“本机已记录，待回传”；不以服务端响应作为成功前提。刷新目录与扫码在本机事务边界排序，单条事实不得混用两版内容；落盘失败不能提示成功。
3. 联网回传时，服务端先按 UUID/原正文哈希幂等重放，已接收直接回原事实，不再检查当前目录或计划是否仍开放；不同正文同 UUID 冲突，不能修改原正文重试。新回传按事实的 `catalogVersion` 查不可变历史条目，验证该版存在/可接受、条码和重量与该版一致及原 ERP 行归属，再事务写事实/context/审计并推进服务端 revision；不能用 head 解析或替换重量。与当前版不同只作独立提示，例如“该包基于 v2，当前目录 v3，重量 300→302kg；已按 300kg 接收”，当前版已移除则提示“当前目录已移除，历史版本事实已接收”。提示不进入事实正文/hash/冻结摘要，不要求人工放行，也不阻止冻结/确认；当前目录差异查询失败不回滚事实接收。
4. 目录只回答“这个码的规格/重量”。ERP 行来自原出库单的作业上下文：单明细直接显示并使用该行，多明细先显式选择当前作业行，扫码区持续展示 ERP 商品和目录规格供核对。保存行归属快照，有事实后不能删换该行或据当前目录重新归类；这不是推测两套商品的全局映射，误选风险须通过现场验收把关。
5. 本地缺码提示“本地 v2 未找到该码，上传新版并刷新目录后可在本单继续扫码”；保留失败尝试供核对，但缺少实重时不生成成功事实。Web 上传后 PDA 联网刷新，再在原单扫码，按新本地版创建事实；已生成的旧事实绝不重新解析。掉响应按原 UUID/正文重传，不能换 UUID 猜重试；本机按 UUID 合并待传与已回传事实、依各自 ERP 行快照累计，禁止再 join 当前缓存归类旧事实。
6. PDA 联网时按 manifest 指定 version 分页下载到暂存区，校验总条数/内容摘要后，在 Room 事务中切换本地指针；中断则保留原完整本地版继续扫码，原计划及所有队列不动。新版下载成功后可在原单继续离线扫描新增码，无需返回列表或重建单据；本地版本既用于浏览也用于离线生成事实，每条记录显示版本与当时重量，**同单多版是正常情况**。
7. 目录相关拒绝只用于该版本不存在/被撤销、从未发布、该版缺码或正文重量与所声明版本不符等数据异常，返回明确原因，原事实进入可见冲突队列，不静默丢弃。被新版本替换不等于被撤销，正常历史版永久保留且可接收；本轮不新增版本撤销流程。仅版本落后、当前版改重/改规格/删码均不得拒绝。既有身份、同 UUID 不同正文、重复条码和单据状态校验不变，不能将目录差异伪装成业务冲突。
8. 冻结仍须完成事实回传并处理真正的冲突；冻结、确认、对账只依赖不可变事实实重及 ERP 行绑定，不 join 当前目录，不要求整单同一目录版本。新版本改重、改规格、删码都不改旧事实；目录发布不改计划版本/revision/冻结摘要，只有服务端首次接收新事实按原规则推进 revision。已记录条码在新版重新出现也不能再次计包，保持现有全局去重边界。

**风险与回退**

三项主要风险：① 本地刷新/扫码竞态及弱网补传造成混版或重复记包，用 Room 原子版本切换/事实落盘、原 UUID/正文重放和服务端接受历史版控制，目录差异仅提示；② 旧冻结摘要、七天窗口和 SPEC/ERP 归属耦合导致历史单无法继续，用不可变 context、旧摘要算法及迁移异常门禁控制；③ 错传全量文件使大量码消失或重量变化，用完整校验、明确差异、整版发布和历史版本保留控制，绝不把“消失”变成自动库存操作。

上线前可回退增量应用并保留已备份 v1；上线后错误目录用“以历史内容发布新版本”恢复，不能回拨版本号、覆盖原事实或以数据库 down 删除历史。若错误新版期间已生成事实，继续保留其原版本/实重供核对，不自动改重或放行差异；事实纠错依后续明确业务流程处理。读/冻结/确认链路须支持已发布的全部事实版本后，才允许回退发布 UI；备份必须能同时恢复版本、条目、head、context、事实及文件 manifest。

- 方案 B：页面、导出、打印各写一份字段映射。优点是局部灵活；缺点是字段变更容易漏改，出现屏幕与打印不一致。

推荐 A，减少长期维护成本。

**收益假设**

同一单据屏幕/导出/打印字段差异 0；筛选到导出 ≤3 步，10,000 行分页导出不占满浏览器内存。测量方式：脚本比较字段 schema、导出表头和打印 DOM；导出大数据时记录内存与耗时；均待实测。

**风险与回退**

历史字段缺失时显示空值并保留列，不改变历史记录；schema 生成器出错时可下载原始 CSV，打印仍可用基础模板。

**收益假设**

连续 100 包离线扫码的成功输入焦点保持率 100%；成功事实 UUID 与正文保持率 100%；网络恢复后合法历史版本事实回传率 100%；真正冲突事实可见率 100%。测量方式：Android 仪器测试在全程断网下连续输入并验证本地成功落盘，再模拟新版改重/删码后回传、响应丢失重试、版本不存在等数据异常并核验 Room 与服务端事实；当前实测只覆盖持久队列和成功同步，分状态可见性及实体扫码枪体验待实测。

**风险与回退**

## 组合与排序

排序按“业务价值 ÷ 成本 ÷ 风险”判断：

1. **B1a 数据正确性，必须与对应 P 同批**：U-02 单号、U-03 重量/确认分层、U-04 原值回退、库存/扫码目录用途隔离、库存调整事务。它们会改变库存或单据事实，须先以接口/E2E 验收。
2. **B1b 共同能力，可独立于 B1a 回滚**：U-01 基础查询壳、O-01 基础响应式/固定列、O-02 导出/打印 schema。它们复用层次高，但不应与库存正确性改动绑成一个提交。
3. **B1c 条码目录（P），建议在现场常态作业前完成**：U-06 的事实快照解耦、Web 全量上传/整版发布、PDA 本地同步版本解析/服务端接受历史版本事实及混版原单继续扫码须完成整体验收；按用户授权拆为 B1c-1 服务端/Web 与 B1c-2 PDA；备份/恢复与 v1 迁移对账是本批门禁。业务价值高于再增加查询页，但需要先稳定 B1a 第 3 提交的确认事务及 ERP 明细边界；不依赖 B1b 导出/打印 schema。两个子批分别验收，整体 B1c 完成仍要求设备端通过，不与 B1b 并行铺开业务页面，也不把它拖到 N-02。
4. **B2，核心 P 后紧接**：撤销审核/作废/更正（补偿事务与下游依赖校验）、O-03 键盘/恢复、O-04 PDA 连续扫码/补传反馈、O-05 小程序查询上下文、U-05 通用备份恢复验证、日志查询、库存查询增强和主数据完整字段。O-04 沿用 B1c 的本地同步版本离线新扫/服务端接受历史版本事实边界。
5. **B3，后置**：盘点、四类报表、消息中心、系统配置、N-01/N-02。它们依赖数据口径、模型或候选批准，适合独立交付；N-02 不再包含目录全量上传。

P0 收敛标准：只保留会改变库存/单据可追溯性、阻断旧 ERP 核心路径，或被两个以上模块依赖的能力；权限因单用户约束为 N/A。

## 现在最值得做但不该做

- **不做多用户/RBAC/多级审批**：单用户没有收益，反而扩大会话、菜单和测试面；除非出现第二个实际使用者并放开约束。
- **不做 PDA 直接扣库存或差异放行**：会突破“PDA 只写事实、Web 明确确认”的边界，库存错误不可接受。
