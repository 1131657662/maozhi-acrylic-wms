# 出库事实来源规范（OUTBOUND_FACT_SPEC）

> 本文档中的状态、类型等库值仅作实现标识；界面显示必须按 docs/UX_STANDARDS.md 映射为中文。

## 1. 一句话

**扫码是辅助，手工录入才是出库事实。**

库存只按「出库明细里人工填写的实发包数 / 实发吨数」扣减，扫码数据不参与库存计算。

## 2. 为什么

- 现场会多扫、漏扫、扫错包；
- 客户要的数量和实际装车数量可能不一致；
- 扫码设备的重量来自条码目录，不是每包都准；
- 出库数量必须以人能确认的数字为准，否则账跟着设备走。

## 3. 数据流

```
PDA 扫码（辅助）
  → 按商品汇总：扫到的包数、扫到的重量（kg）
  → 预填到出库明细：实发包数、实发吨数（kg × 0.001）
  → 人工修改（可改、可清空重填）
  → 确认出库
  → 库存按人工数字扣减
```

## 4. 字段

### 出库明细（outbound_lines）

| 字段 | 说明 |
|---|---|
| planned_packages / planned_weight_tonnes | 计划，可改（见第 6 节） |
| scan_packages / scan_weight_grams | 确认时的扫码汇总快照，只读，供追溯 |
| actual_packages / actual_weight_grams | **人工确认的实发量，库存依据**；由发货记录行汇总得出，**不是独立列** |
| memo | 行备注 |

规则：
- `actual_*` 未填不允许确认；
- 实发由 `outbound_shipment_lines` 汇总（读模型），不单独落列，避免双写不一致；
- 预填值来自 `scan_*`，但两者独立：扫码后来变了，不改已确认的实发；
- `scan_*` 可为空（没扫码也能手工出库）。

### 单据（outbound_orders）

保留计划合计与实发合计两个口径，界面分开显示。

## 4.1 同一商品多行

一张出库单里**同一商品可以出现多行**（不同合同号、不同备注、不同用途）。扫码只按商品汇总，无法区分行，因此预填按以下规则：

1. 某商品的扫码汇总 = 包数合计 + 重量合计（kg）；
2. 该商品的多行按**行顺序**依次填满：
   - 第 1 行填 min(剩余扫码包数, 该行计划包数)；
   - 剩余继续填第 2 行，依此类推；
   - 扫码数超过全部计划时，超出部分填在最后一行；
3. 重量按各行预填包数的比例分配，保留 4 位小数，最后一行吃掉舍入差；
4. 预填后该商品各行标注「按扫码预填，请核对」；
5. 用户可逐行修改，修改互不影响；
6. 确认时按**每行自己的实发量**扣库存，合计即为该商品总出库量；
7. 若该商品各行实发合计与扫码汇总不一致，确认弹窗提示差异，但不阻断（以人工为准）。

## 5. 界面

### 出库详情 · 明细表

| 列 | 说明 |
|---|---|
| 商品 | 编码 + 名称 |
| 计划包数 / 吨数 | 只读（计划状态可改） |
| 扫码包数 / 吨数 | 只读，灰色；无扫码显示「未扫码」 |
| **实发包数** | 输入框，预填扫码值；B5c-3 起页面空白按 0 提交 |
| **实发吨数** | 输入框，预填扫码重量换算值，4 位小数；B5c-3 起页面空白按 0 提交 |
| 差异 | 实发 − 计划，正数标蓝（溢发）、负数标橙（短发） |

### 确认弹窗

```
确认出库
本单将扣减：90 包 / 27.0000 吨
其中 3 行与计划不一致：
  003 计划 40 → 实发 38（短 2 包）
  007 计划 30 → 实发 32（溢 2 包，需填原因）
[取消] [确认出库]
```

规则：
- 弹窗只显示实发数字，不显示扫码数字；
- 与计划不一致的行单独列出；
- 溢发必须填原因（B5c 实现）。

### 扫码记录

- 出库详情提供「扫码清单」面板：条码、商品、重量、扫描时间；
- 支持导出（XLSX），一次导出本单全部扫码记录；
- 导出文件含合计：包数、重量（kg 与吨）；
- 扫码记录只读，不可编辑、不可删除。

### 5.1 Web 清点工作台

PDA 扫不出、条码破损、人不在现场、或需要复核数量时，在 Web 上完成清点。

**定位不是“补录一个条码”，而是一个完整的清点工作台**：把扫码、手输、批量粘贴、进度、带入实发放在同一处，清点完一键把结果带入实发表单。

#### 三种录入，一条通道

| 方式 | 输入 | 行为 |
|---|---|---|
| 扫码枪 / 键盘 | 完整条码 + 回车 | 精确命中直接计入 |
| 片段搜索 | ≥4 位 | 出候选，勾选后「计入选中」 |
| 批量粘贴 | 每行一个条码 | 先校验，再一次性计入 |

三种方式最终都写入同一条「扫码记录」，只是 `source` 不同：`scanner` / `search` / `paste` / `manual`。

#### 批量粘贴（参考项目没有的关键能力）

```
粘贴 20 行 → [校验]
→ 有效 17 条（可直接计入）
→ 重复 2 条（本单已有）
→ 无效 1 条（目录无此条码 / 不属于本单）
→ [仅计入有效 17 条]
```

一车货标签打印出来是一张纸，粘贴比一条条敲快得多。

#### 智能匹配

1. 条码 → 商品 → 本单对应行；
2. 同商品只有一行 → 自动归到该行；
3. 同商品多行 → 记录绑定原单该商品首行；预填仍按 §4.1 按商品汇总后依行序分配；
4. 请求必须带 `productCode`，不在本单时返回 422 与可选商品；可靠目录映射与所选商品不一致时返回 422 并提示条码所属商品；
5. 可靠映射指目录 `legacy_product_code` 精确关联有库存资格的商品，不猜测 SPEC 与 ERP 的关系。映射一致记录 `attribution=catalog`，无可靠映射允许操作者确认归属并记录 `attribution=manual`；
6. 「当前商品」单商品自动选中，多商品默认第一个有待发数量的商品（都无待发则第一个）；粘贴按当前商品归属，记录表对 manual 标「归属人工确认」。

#### 进度与带入实发

- 顶部实时显示：计划 / 已录 / 差额，包与吨分开；
- 「带入实发」把当前已录的包数与吨数填进出库明细的实发输入框（仍可修改），不自动确认；
- 已录数超过计划时，差额标黄并提示「已超计划 N 包」。

#### 记录与撤销

- 记录表显示：时间、条码、商品、重量、来源、操作人；
- 支持按来源筛选（只看手工 / 只看扫码）；
- 「撤销上一条」撤销最近一条未确认记录，保留原 UUID、正文与撤销人/时间，不物理删除；进度、预填、导出只读未撤销记录；
- 本单已撤销条码再次录入仍返回「已录入（已撤销）」，不复用 UUID、不覆盖旧归属；
- 已确认出库后不可删，只能走更正；
- 记录不可编辑。

#### 与实发的关系

```
扫码记录 → 只做计数与预填
实发数量 → 人工填写（可一键带入，仍可改）
库存扣减 → 确认出库时按实发
```

#### 接口

| 接口 | 说明 |
|---|---|
| `GET /outbound/:id/scan-candidates?query=&productCode=&page=` | 本单范围内候选，条码片段/完整条码 |
| `POST /outbound/:id/scan-records` | 单条计入 `{ barcode, productCode, source }`，幂等 |
| `POST /outbound/:id/scan-records/batch` | 批量计入 `{ records:[{ barcode, productCode }], source:'paste' }`，同批允许多商品，逐条返回结果 |
| `DELETE /outbound/:id/scan-records/:recordId` | 仅未确认时 |
| `GET /outbound/:id/scan-summary` | 计划/已录/差额与按商品汇总 |

规则：
- 批量接口逐条校验、逐条返回成功或原因，不做整批回滚（允许部分成功）；
- 同一幂等键重复提交不重复写入；
- 条码唯一性按「订单 + 条码」判定。

#### 权限与审计

- 仅登录 Web 可操作；
- 每次计入写审计：条码、来源、操作人、时间、结果；
- 撤销写审计，保留原记录 ID。
- 计入审计同时记录 productCode、source、attribution；批量逐条事务、逐条留证，重放沿用各条命令键。
- 018 在原表新增可空 source、attribution、revoked_at、revoked_by；历史值保持 NULL，展示「历史未记录」。唯一约束改为订单 + 条码，down 在 DDL 前检查新列证据及跨单重复，任一存在拒绝回退。
- 候选每页 20 条、批量最多 200 条、片段至少 4 字，均用共享常量；输入不足 4 字但精确命中完整条码仍可返回。候选只含当前本单商品的可靠映射及需人工确认归属的无映射条码。
- 已结束扫码须先重新开启再计入；确认/终结单据只读。Web 不改变 PDA 已确认补传的兼容协议。

#### 边界

| 情况 | 处理 |
|---|---|
| 目录里没有该条码 | 拒绝，提示「目录无此条码，请先更新目录」 |
| 条码属于其他商品 | 拒绝，提示所属商品 |
| 条码已在本单 | 拒绝，提示「已录入」 |
| 超过计划 | 允许，标黄提示 |
| 单据已确认/短关 | 拒绝，只能看 |
| 批量里混有无效项 | 有效项照常计入，无效项列原因 |
| 并发两个窗口 | 幂等键 + 唯一约束，只写一次 |

## 6. 计划与实发的关系

| 项 | 规则 |
|---|---|
| 计划可改 | 计划中、部分发货状态可改；已出库、已短关不可改 |
| 计划不扣库存 | 计划只是参考，不预占 |
| 实发可改 | 确认前可反复改 |
| 实发决定库存 | 确认时按实发扣减 |
| 短关 | 剩余不发，结单，不动库存 |
| 溢发 | 允许，按实发扣，原因必填 |
| 状态 | 计划中 → 部分发货 → 已出库 / 已短关 |

## 7. 单位与换算

- 扫码重量单位是 **kg**，界面展示为吨时除以 1000（4 位小数）；
- 接口与发货行使用整数克（`actualWeightGrams` / `weight_grams`，100 克精度）；库存沿用 DECIMAL(12,4) 吨，精确整数换算，不存浮点 kg；
- 换算只发生在预填与展示，不改变原始扫码记录。

## 8. 边界

| 情况 | 处理 |
|---|---|
| 没扫码直接手工出库 | 允许，扫码列为「未扫码」 |
| 单行实发填 0 | 允许，该行不发；全单包数和重量均为 0 时拒绝，空值仍拒绝 |
| 扫码 40、实发填 45 | 允许（溢发），需原因（B5c） |
| 扫码后又有补传事实 | 只更新扫码列，不覆盖已填的实发 |
| 扫码记录缺失条码目录 | 导出中标注「目录缺失」，重量按 0 计并提示 |
| 已确认后再补传 | 不改单据实发，扫码记录追加，供核对 |

## 9. 验收

1. 扫码 40 包 / 12000 kg，明细预填 40 包 / 12.0000 吨；
2. 人工改为 38 包 / 11.4000 吨，确认后库存扣 38 包 / 11.4000 吨；
3. 同一单再导出扫码清单，仍显示扫码的 40 包 / 12000 kg；
4. 不扫码直接手工填 20 包 / 6.0000 吨，可正常确认；
5. B5c-3 起实发留空按 0 提交，全单全 0 禁止确认；原 B4d 页面空白必填验收规则由此取代；
6. 扫码记录导出含条码、商品、重量、时间与合计；
7. 同商品两行：扫码 50 包，计划第一行 40、第二行 30 →
   预填 40 / 10，重量按比例分配，最后一行承担舍入差；
8. 把第二行实发改成 8，确认后该商品总出库 48 包，库存按 48 扣。

### 9.1 清点工作台

9. 完整条码回车 → 立即计入，进度 +1；
10. 输入 4 位片段 → 出候选，勾选 3 条 → 计入选中，进度 +3；
11. 批量粘贴 20 行（含 2 重复、1 无效）→ 计入 17 条，结果逐条给原因；
12. 「带入实发」后明细输入框被填入，手工改数字仍可确认；
13. 「撤销上一条」后进度 −1，导出中该条消失；
14. 已确认出库后再次打开工作台 → 只读，撤销按钮不可用；
15. 并排两个窗口同时计入同一条码 → 只写入一条。

## 10. 与分批发货的关系（B5c）

- B4d 的确认动作按「创建第 1 条发货记录」实现，本次数量默认等于全部待发；
- `outbound_lines.actual_*` 由发货记录汇总维护，不独立双写；
- B5c 增加第 2、3 次发货时，`actual_*` 继续等于累计汇总；
- 计划修改只影响待发，不影响任何发货记录；
- 更正作用于发货记录行，不改 `scan_*` 快照。

## 11. B4d 实施边界（2026-11-11）

- 本轮 open/frozen 都可在 Web 填实发后确认，一次确认仍转 confirmed；多次发货、短关与新状态流留 B5c。
- 016 新增发货表及扫码快照；行序 `line_position` 保留新建明细顺序，旧行按原稳定 ID 顺序读取，不伪造历史发货记录。
- 实发读模型直接按发货行汇总，无独立可写的 actual 列；升级前已确认无发货记录的单据保留原扫码取值。确认后的补传仅允许本批已有发货记录的单据，避免改变旧确认数量。
- 已确认的 scan_* 为确认时分配快照；扫码清单继续追加补传，不能覆盖快照、实发或库存。
- 同商品各行实发先按商品合并再扣库存；第 1 条发货的 business_date 沿用单据业务日期（无记录时取上海确认日），shipped_at 为真实确认时间。
- 扫码清单为登录 Web 专用下载，10 万行上限；完整生成 XLSX 后才发送，文本作为文本单元格，不输出半文件。

清点工作台（§5.1）**不在 B4d**，单独排 **B4g**：B4d 只做手工实发、发货记录 #1、扫码预填与快照。

- 经确认：016 将更正明细主键由“更正单 + 商品”改为“更正单 + 原单行”，既有行原值回填；同商品多行的更正、撤销按商品合计核验库存证据。关联发货记录行仍属 B5c。非空更正明细同样阻止 016 down。

- 本轮初始边界曾不新增 scan_closed_at、不拆分 frozen；该决定已被下方 §12 的收尾补修裁定取代。重量舍入差归最后一个分得包数的行，后续未分得包数的行保持 0/0。

## 12. B4d 收尾补修（2026-11-11）

- 原 submit/freeze 接口仅允许 open，去掉扫码与计划相等门槛，只写 scan_closed_at，返回「已结束扫码」，不改 status、不扣库存。
- 新增 POST /outbound/:id/scan-reopen，Web 登录校验、修订号与摘要、逐单锁、幂等键；仅 open 且无发货记录可清空标记，记录审计。旧 scan_submissions 作为历史证据保留，结束/重开不覆盖旧记录。
- 结束扫码后拒绝新扫码；已收到的 UUID/正文仍可原样重试。B4d 已确认单的离线补传继续兼容，不改变实发、扫码快照或库存。
- 016 新增 outbound_orders.scan_closed_at DATETIME(3) NULL；历史 frozen 转 open。当前表无 updated_at，回填依次取 scan_submissions.created_at、最新 scan.freeze 审计时间、建单时间；兜底不冒充精确结束时间，迁移记录披露来源。
- confirm 仍兼容 open/frozen，确认时 scan_closed_at 为空才自动填入，使用与既有 DATETIME 相同的 UTC 存储、上海时区展示。
- 016 down 在任意 DDL 前检查发货两表、扫码快照、非默认行序、更正证据与 scan_closed_at；任一有证据则拒绝，不删列。
- 日期显示统一公共 sv-SE / Asia/Shanghai formatter，页面、错误时间和 XLSX 均显示 YYYY-MM-DD HH:mm:ss。
- PDA 仅做本次协议兼容：依据 scanClosedAt 禁止新扫码和重复结束、展示结束状态；不改队列、事实正文和原有补传协议。实体设备验收另记，不以 API/E2E 代替。
