# 设计决策

本轮文档已确定三项业务口径：入库单号使用 `RK-YYYYMMDD-####`、出库单号使用 `CK-YYYYMMDD-####`；用途隔离，库存与单据只认 `erp-product`，`sku-spec` 仅属于 B1c 条码目录页面；差异放行/短装超发本轮不做。所有 U 指标都包含测量方法；没有真实运行数据的位置明确标记“待实测”。

## DD-01 统一列表壳

- 问题：B1b-1 前原型各页独立筛选，库存全量取回、日志只取最近 100 条；旧入库读取每条明细造成多次查询。旧实现保存在父提交 f7a8c070；当前实现为 [BusinessList](../apps/web/src/components/BusinessList/index.tsx)、[分页查询](../apps/api/src/features/web-lists/query.ts)，不再引用已改写文件的旧行号。
- 方案：四页共用 PageContainer + QueryFilter + ProTable，URL 保留筛选/排序/页码，列设置按页版本化存 localStorage；日期按上海时区整日边界；新 Web 只读端点独立，旧移动端契约不改。计划与实扫分开聚合，库存小计只认相同筛选的 ERP 有效行。
- 布局决策：单号/商品名称/动作左固定，单据原始状态与行操作右固定；包数/吨数前置，避免窄屏先看到辅助字段。内边距使用 token.paddingLG，减少嵌套容器的横向留白；表体最大高 480px（4 的倍数），让 200 行在表内滚动，未重写默认行高/密度或 .ant-*。
- 备选：四套独立列表或一次拉全量前端筛选；否决理由为口径/列设置漂移及数据量增长。选中不等于批量确认，跨页保留选择、筛选变化清空；XLSX导出在B1b-2复用查询与列配置；打印已延后，后续只代理积木PDF，不用列表schema生成版式。
- U 指标与基线：同机临时 MySQL 10k 行各 30 次，旧入库 50 行查询 p95 303.62ms → 新 35.04ms；新第 200 页 37.27ms。旧库存全量查询 12.43ms、新带筛选小计 84.88ms，不能声称 SQL 全面提速；收益为传输/渲染上限 200 行。日志由截断 100 条改完整分页。生产构建浏览器首屏/翻页 30 次 p95 与运行条件见 ACCEPTANCE，本批不杜撰旧人机点击/耗时。
- 验证方法：E2E [web-lists](../tests/e2e/web-lists.spec.ts)、[四态](../tests/e2e/web-list-states.spec.ts)、[列设置/跨页选择](../tests/e2e/web-list-preferences.spec.ts)；[SQL/旧新读模型计时](../scripts/verify-list-performance.ts)、[生产构建浏览器计时](../scripts/verify-list-browser-performance.ts)。1440/1280 图片存 .local/evidence/b1b1-{inbound,outbound,stock,audit}-{width}.png；这是合成隔离数据验收，不代替生产/真人计时。
- 回退：单独 revert B1b-1 提交即可撤回新 Web 路径与只读端点；没有新增依赖、迁移或业务写入；保留 B1a/B1c 的库存/目录事务与旧 API。首次扩充测试触发登录限流后，仅列表测试改用临时库专用会话，保留登录 UI 测试和真实限流。

## DD-02 入库重量独立录入

- 问题：样本包重 60–389.5kg，9018 条条码实重独立存在（[sku-analysis.json](../.local/prod-sample/sku-analysis.json)）；统一件重会把估算写成事实。
- 方案：明细分别录包数和总吨数，实时累计但不反算；差异只提示或按配置校验。
- 备选：输入件重后乘包数；否决原因是违背每包重量不同的业务边界。
- U 指标与基线：新建目标 ≤2 屏，重量差异静默提交 0 次；当前表单已有两个独立字段（[inbound/editor.tsx（112–123 行）](../apps/web/src/features/inbound/editor.tsx#L112)，差异提示耗时待实测）。用 E2E 10 组差异输入和字段焦点序列测量。
- 回退：历史异常只警示，新单硬校验可由 feature flag 关闭；不改历史重量。

## DD-03 出库冻结与确认分层

- 问题：旧 ERP 审核直接联动扣库存（[outbound_order.js（443–536 行）](D:/wms-new/wms-backend/controllers/outbound_order.js#L443)）；PDA 冻结若被当成出库会误扣。
- 方案：PDA 只写不可变扫码事实并冻结；Web 详情展示包级实重，确认事务同时写库存、流水、审计和幂等结果。
- 备选：PDA 提交直接扣库存；否决原因是突破 AGENTS 的 Web 明确确认边界。
- U 指标与基线：重复确认 0 次重复扣减；当前 API 已用事务和命令回放（[confirm.ts（25–36 行）](../apps/api/src/features/outbound/confirm.ts#L25)），E2E 已覆盖一次确认，重复请求和确认前后用时待实测。用同一幂等键重放 3 次并核对库存/流水。
- 回退：确认失败事务回滚，保留扫码事实；测试环境可关闭新确认按钮，历史记录不回滚删除。

## DD-04 RK/CK 自动单号

- 问题：提案基线两个 ProForm 各需手填单号；旧 ERP 已有事务序列生成器（[bill_no.js:11](D:/wms-new/wms-backend/utils/bill_no.js#L11)）。B1a 第 1 提交已移除手填控件。
- 方案：入库 `RK-YYYYMMDD-####`、出库 `CK-YYYYMMDD-####`；北京时间日序列、服务端事务取号，配置页非占号预览，最终号以创建成功响应为准；宽度只改补零。
- 备选：前端独自计算预览；因无法校验历史占用及服务端业务日而否决。服务端预览同样不锁定未来单号，不把它承诺为预约号。
- U 指标与基线：每单少 1 个手填字段；两类各 50 个并发 HTTP 创建 0 重复，[numbering-concurrency.test.ts](../apps/api/tests/numbering-concurrency.test.ts)；建单时长/键盘草稿仍待实测。
- 回退：未提交事务同时回滚计数器；已提交号保留；Web/API 成套回退并保留非空 004 表；旧客户端原号兼容带弃用头，编辑仅可原样回传，不允许改单号。

## DD-05 库存与扫码目录用途隔离

- 问题：`sku.txt` 的 9018 条包级记录、141 条规格是条码→规格+实重的扫码目录，不是库存；将其作为库存入口会制造不存在的业务口径。库存唯一依据是 428 个 ERP 商品的 `source_kind='erp-product'`。
- 方案：库存与单据只认 ERP；库存页固定 ERP 查询、汇总、明细和流水，不显示来源切换。SPEC 仅属于 B1c 条码目录页面（B1c-1 Web 已验证）；未归属记录只在诊断日志提示行数，无用户入口。API 防混源参数守卫及严格响应校验保留。
- 备选：保留 SPEC/未归属空页签；否决原因是暗示存在另一套库存，即使当前没有数字也会误导。按名称/前缀自动映射同样禁止。
- U 指标与基线：原库存页 3 个入口改为唯一 ERP 视图，非 ERP 用户入口、请求及占位均为 0；[E2E](../tests/e2e/stock-source.spec.ts) 检查无页签、只请求 ERP、错源拒绝及四态；[API 测试](../apps/api/tests/stock-source.test.ts) 验证参数守卫和仅诊断日志提示。9018 条目录关联沿用原 DATA 基线。
- 回退：本次无迁移，可整体回退代码；已否决的库存入口不得重新作为业务设计发布。原商品、库存、历史单据和条码目录数据不变，缺少可靠关联键继续留 B1c 核对，禁止猜测。

## DD-06 状态与流水类型原文回退

- 问题：真实状态有 `audited`/`submit`，流水类型有 `check`/`import`；基线只在出库部分映射。B1a 第 1 提交已统一为 [StatusTag](../apps/web/src/components/StatusTag/index.tsx#L1) 与 [JournalTypeTag](../apps/web/src/components/JournalTypeTag/index.tsx#L1)，不替历史猜含义。
- 方案：数据库保留原字符串；未知状态显示“状态待识别：原文”，详情常驻说明尚不能判定出入库、核对原始单号的下一步，以及出库确认禁用。库存常驻展示“库存口径：ERP 商品”，关键说明不依赖 tooltip。
- 备选：导入时强制映射到有限枚举；否决原因是历史语义不可逆。
- U 指标与基线：B1a 第 1 提交已用真实测试库未知值验证入/出库列表、详情及最近流水：0 空白、0 页面异常；报表未实现，不纳入已完成范围。见 [numbering.spec.ts:89](../tests/e2e/numbering.spec.ts#L89)。
- 回退：组件异常时显示纯原文字段，不修改数据库值。

## DD-07 库存调整与盘点回写

- 问题：旧系统有库存调整和盘点，当前原型无可靠调整界面；直接编辑库存会破坏流水连续性。
- 方案：调整和盘点都经过原因必填的确认抽屉，在同一事务写库存、原值/新值流水、操作日志和幂等结果；盘点先生成快照。
- 备选：直接在库存表编辑数字；否决原因是无法审计前后值。
- U 指标与基线：每次调整审计/流水覆盖率 100%，错误调整可由补偿事实恢复；当前没有可测 UI 基线，接口事务 E2E 待实测。用正负包数/吨数、重复提交和回滚场景测量。
- 回退：调整失败只回滚事务；盘点差异回写失败保留快照，不删除盘点单。

## DD-08 报表性能与口径

- 问题：四类报表需要按日期、仓库、ERP 商品聚合，前端全量计算会拖慢并占内存；样本已有 828 条流水，其中有效 804 条、软删 24 条。
- 方案：固定 `erp-product` 用途边界后按日期/仓库聚合，组合索引和服务端分页；SPEC 扫码目录不进入报表。导出按分页流式生成，字段顺序与屏幕一致，软删口径显式显示。
- 备选：前端拉全量后计算；否决原因是数据量增长后首屏和浏览器内存不可控。
- U 指标与基线：首屏 p95 <1.5s、翻页 p95 <500ms；当前样本规模 122 库存/828 流水仅用于正确性，不代表性能基线，10k 行性能待实测。用 SQL EXPLAIN 和 API p50/p95 脚本测量。
- 回退：报表查询错误可原筛选重试；导出失败/超时不给部分文件，重新核对后发起任务，不宣称支持断点续导；不将扫码目录或未归属记录混入库存统计。B3b实际取舍见DD-18。

## DD-09 单用户权限边界

- 问题：手册含用户/角色矩阵，但 AGENTS 明确单用户；旧权限页会增加配置和误授权面。
- 方案：保留登录、会话、Web/PDA/小程序 channel 边界、操作日志和备份恢复；权限矩阵和多级审批记 N/A。
- 备选：照搬管理员/审核员/操作员角色；否决原因是没有实际第二使用者且违反项目约束。
- U 指标与基线：权限配置点击和角色维护目标 0；当前 owner 登录和错误 channel 拒绝已有 E2E，完整越权矩阵待实测。用三种 channel 交叉请求验证。
- 回退：出现第二个实际使用者时作为独立架构项目重新设计，不临时塞角色。

## DD-10 导出字段 schema

- 问题：旧系统列表导出和详情导出各自维护（[InboundOrderList.vue（444–537 行）](D:/wms-new/wms-frontend-pure/src/views/wms/InboundOrderList.vue#L444)、[InboundOrderDetail.vue（107–148 行）](D:/wms-new/wms-frontend-pure/src/views/wms/InboundOrderDetail.vue#L107)），屏幕、Excel 和打印易漂移。
- 方案：B1b-2 四列表与 XLSX 共用 `listFields/listCellText`；实际可见列顺序（含固定/隐藏/拖动）传给白名单接口。全部筛选/当前页/选中先显示数量，生成后展示独立范围合计；每1000条在同一只读快照内读取，复用该快照总数/库存小计。XLSX 写真实数字/日期、吨数四位、上海时间，标识符始终文本。CSV本批不做，打印已延后，依赖积木报表配置，不能声称打印已同源验收。
- 备选：浏览器一次拉全量，或边下载边生成；否决原因是内存随记录数增长、失败留下半份文件。采用服务端 ExcelJS 4.4.0 流式 writer、禁用共享字符串；完成后校验 SHA、原子改名才开放下载；第二任务409明确提示，不隐式排队。
- U 指标与基线：原型无导出；四页×三范围及列重排共13组真实DOM→XLSX逐字段对比，目标/实测差异0（原始输出见ACCEPTANCE）；使用 `tests/e2e/web-exports.spec.ts` 和 `scripts/verify-export-performance.ts` 测量完整性、末条、生成耗时、内存、生成中翻页。选择默认全部时：打开面板→生成→下载共3次点击；改变范围另加1次。真人计时与Microsoft Excel实开待测，WPS实开不冒充Excel。
- 风险与回退：不在失败后绕过字段/快照校验提供原始CSV；保留输入，显式重试。完整文件24小时有效；服务重启的运行中任务失败关闭，不跨快照续写。revert本批源码/依赖提交可回退，无迁移及业务数据重写；原列表仍可用。单进程任务锁符合当前部署，多实例部署前须另行设计协调。

## DD-11 打印模板

- 状态与问题：**已延后，依赖积木报表配置，未完成。** 用户确认旧ERP版式由积木报表保证，旧方案中的自建A4/HTML模板作废。

- 风险与回退：配置缺失/代理失败明确提示且不改库存或单据；可停用打印入口/回退配置。不能降级为自制HTML模板；token不进仓库/日志，原PDF不重排。

## DD-12 PDA 连续扫码与离线补传

- 问题：PDA 已持久化事实并在联网时重试（[ScanRepository.kt:8](../apps/pda/app/src/main/java/cn/maozhi/wms/pda/scan/ScanRepository.kt#L8)、[SyncWorker.kt:19](../apps/pda/app/src/main/java/cn/maozhi/wms/pda/sync/SyncWorker.kt#L19)），但主屏只显示队列总数且补传遇首个失败即退出本轮（[ScanScreen.kt:23](../apps/pda/app/src/main/java/cn/maozhi/wms/pda/ui/ScanScreen.kt#L23)、[SyncRepository.kt:11](../apps/pda/app/src/main/java/cn/maozhi/wms/pda/scan/SyncRepository.kt#L11)）。现场需要连续录包并立刻知道失败、冲突和回传结果。
- 方案：扫码主屏保持输入焦点，显示最近扫码结果及待回传/失败/冲突/已回传分类；网络错误自动重试，真正冲突进入核对队列。B1c/DD-15 定义“本地同步版本 + 服务端接受历史版本事实”：常态断网扫码成功落盘，回有网处回传/刷新；当前目录改重或删码只提示，不阻断合法历史事实。
- 备选：把状态放在独立记录页；否决原因是现场需离开扫码流程才能确认是否漏传。
- U 指标与基线：当前仪器测试覆盖本机队列持久化和冻结不扣库存（[ScanIntegrationTest.kt:21](../apps/pda/app/src/androidTest/java/cn/maozhi/wms/pda/ScanIntegrationTest.kt#L21)），连续 100 包离线扫码焦点保持、错误分类可见性和实体扫码枪体验待实测；目标焦点保持率、冲突可见率、合法历史版本事实回传率均 100%。用 Android 仪器测试模拟全程断网新扫 100 包、新版改重后补传、版本不存在等真正冲突，并另做实体设备扫码枪计时。
- 回退：异常时回到当前扫码记录/补传入口；Room 中 UUID 与正文不可变，任何重试都不删除或重写事实；PDA 永不确认出库或扣库存。

## DD-13 小程序只读查询上下文

- 备选：每次返回均重载第一页；否决原因是反复滚动/翻页会增加单手操作步骤。

- 回退：缓存过期时保留原列表并刷新当前页，失败显示“刷新失败，请重试”；页面生命周期异常时恢复现有第一页重载行为。小程序不扫码、不写事实、不改库存。

## DD-14 备份产物校验与隔离恢复演练

- 问题：备份脚本生成 SQL 但没有摘要清单（[backup.ts:7](../scripts/backup.ts#L7)）；恢复脚本会恢复到新库并在失败时清理，但不做摘要和数据级完整性对账（[restore.ts:7](../scripts/restore.ts#L7)）。仅“备份命令成功”不能证明产物可恢复。
- 方案：每份备份附 SHA-256、大小、数据库身份和时间 manifest；先在隔离新库恢复，再核对身份、关键表行数与重量汇总；通过后仍由人显式决定是否切换。
- 备选：只定期人工抽查页面；否决原因是不能稳定发现文件截断或历史行缺失。
- U 指标与基线：当前无摘要 manifest 和数据对账步骤，恢复时长待实测；目标产物摘要校验率、恢复身份校验率和约定数据对账通过率均为 100%，隔离恢复耗时 <15 分钟。用单字节篡改样本、恢复新库并比较 manifest、表计数和重量汇总；每次迁移验收演练计时。
- 回退：失败只清理本次隔离恢复库，保留原备份和当前开发库；若自动对账有误，回到人工只读对账，不自动切库、不连接生产。

## DD-15 条码目录整版发布与事实独立追溯（B1c-1/2 本地与 M71 隔离验证）

落地补充：原文件采用同库 MEDIUMBLOB，避免文件与数据库双写；每版保留 source/content 两种 SHA。任一历史版内容相同默认不建版，显式二次确认才重建。发布门禁为部署开关、006/context 就绪及持久旧协议/未核实队列计数均通过，页面显示原因，不自动过期。旧 scan_catalog 变为不可更新 v1 视图，archive 三种 DML 触发器拒绝；非空版本禁止 down。Web 选择文件后失败保留输入/原请求键，已提交丢响应按上传 UUID 核验；刷新可从历史继续候选。9018 行本机 3307 的 20 次测试：解析+差异+候选提交 p95 176.88ms，发布事务 p95 25.97ms；不是网络/实体设备性能结论。

- 问题：旧 PDA 已有 SKU 版本/导入/云更新（[V10SkuActivity.kt:101](D:/wms-new/wms-pda/app/src/main/java/com/jinglun/wmspda/ui/V10SkuActivity.kt#L101)），属于 P。计划基线版本锁死 v1；本批 [repository.ts](../apps/api/src/features/outbound/repository.ts) 已改按 context 归属，PDA ScanRepository 已按本地版本落盘并保存旁表 context；用户缺码补传目录后必须在原出库单续扫，不能让删码或改重破坏冻结/确认。
- 方案：采用 U-06 的不可变整版 entries/versions、单行 head 与 fact context；Web 同页展示全量校验/差异后一次发布，历史在抽屉；消失码无失效审批、不自动扣库存。目录容器最大 1440px、抽屉最大 720px（均为 4 的倍数且随视口收缩），为条码/规格/新旧重量留出空间；其余沿用 token，不改组件默认密度。每条事实保存版本/规格/实重及原单 ERP 作业行绑定，同单可混版。“最新版”是 PDA 上次完整同步的本地版：本地同步版本 + 服务端接受历史版本事实，断网扫码成功落盘，联网按原 UUID/正文回传；新版改重/删码只给已接收差异提示，不改事实、不拒收，冻结不 join 当前目录。规格不模糊匹配 ERP，目录/库存/单据用途隔离。
- 备选：当前表 + SCD 区间历史能省空间，但增加移除/重现/并发重建风险，按需更新约 9k 条规模不选；按整单固定目录版本虽简单，却无法让原单扫刷新后的新增码，也否决；每包在线解析违背现场常态断网，不采用。Web 仍是权威发布入口，USB 本机覆盖不替代可追溯的服务器发布/同步版本。
- U 指标与基线：现状无 Web 上传且 v1 硬编码，时延基线待实测；目标全量解析/差异 <10s、发布事务 p95 <500ms、历史事实变化 0、原单重建 0、逐包版本/实重追溯 100%。U-06 场景 A 保留缺码补目录后原单混版冻结/确认；场景 B 明确第一段全程断网扫 3 包→回传→上传新目录→刷新→原单继续离线扫，并验证新版先发布仍接受旧版回传。API 故障注入/Playwright/Android 仪器测试及实体 PDA 分档测量，本批 Web/API 场景 A、坏文件/事务故障、同内容去重与历史事实回传已验证；M71 隔离包以 100 条全程断网、60*v1+1*v2 原单与逐字原文比对验证核心路径，真实业务/硬件扫码枪仍未验收。
- 风险与回退：Room 1→2 只加表、旧正文不动；原子切换/落盘、历史版校验和幂等结果避免混版/重复；目录相关仅不存在/被撤销等数据异常拒绝并保留可见冲突，不把版本落后/改重提示当冲突。事实归属、旧 digest 算法和旧队列先核验迁移，再开放上传；不改旧 UUID/正文/hash/实重。错误文件整版不动；错误已发布版以新版本恢复旧内容，已有事实不自动改重。产生新版本事实后只停新发布、保留兼容读/补传/冻结/确认，不回退只懂 v1 的代码、不 down 删除版本数据。B1c-2 交接记录原正文 SHA/清单 SHA/已收妥及旧请求水位；Web 原单批量绑定，上报不足不可解除。M71 实测事务未提交中断后旧 APK 可开原队列；成功升级后仅前向修复，不能据此任意降级。

## DD-16 误确认反向补偿与未入账作废（B2a）

- 问题：单用户误点确认后需要恢复账务，但原事实/下游出入库不能被覆盖；尚未入账的重复单应能结束且永久保留原号。实物退货另行排期。
- 方案：原详情复用一套纠错Card与560px抽屉（4的倍数，为逐项前值/补偿/后值和原因留空间，沿用默认token）；提交前给出原操作、原流水和阻断证据。先全局库存写锁再单据锁，依赖复验后同事务生成补偿、终态、审计和幂等；原操作唯一关联避免异键重复补偿。
- 备选：把confirmed改回open/pending或覆盖原流水虽少表，但会重开扫码/重复确认并丢失原始账务，否决；仅余额够扣便撤销会误伤后续操作，也否决。按同仓商品后续有效流水保守阻断，不推测FIFO或自动级联。
- 已定边界：只处理本地原确认可验证单据；历史原状态只读。入库cancelled/reversed、出库cancelled，作废voided且无库存流水；原号不复用、不重新开放扫码。迁移前旧计划视为下发不明，新PDA获取计划在响应前持久记下发；有事实/冻结/交接/下发则禁止未入账出库作废，留B2b收妥规则。
- U测量：此前原型无纠错入口、旧ERP人机基线待实测，不虚构节省时长；当前目标为原详情打开抽屉→填原因→确认3步，原单重建0、事实变更0、20并发仅1补偿、delta净0。用document-lifecycle.spec.ts和lifecycle-reverse.test.ts记录实际输出，输入恢复与下游阻断另测；本批按P交付，不以安全断言充当人机提速结论。
- 风险/回退：未知历史、余额缺口或任何后续动作阻断；逐写入点故障及多商品中途失败须全回滚。空表008可down，有下发/终态/库存操作数据即拒绝；有新终态后保留兼容读取和原事实重试，禁用新写入口并前向修复，不能回到会重开原单的实现。终结不清理任何离线队列。

## DD-17 固定快照、仓库暂停与人工回写（B3a）

- 问题与基线：盘点中仍有现场收发、离线扫码和补传；把“实盘−当前库存”回写会漂移，遗忘结束会长期阻断确认。原型无盘点入口，旧ERP录入时长待实测，本批不宣称人机提速百分比。
- 方案：009将不可变快照和可修改实盘分表，生成快照同事务建立仓库持久暂停窗口；库存writer锁仅覆盖开始/完成/作废短事务。菜单数量常驻，单张直达；正常完成或作废释放，进行中只有作废可提前释放，无手动/超时解锁。
- 布局/容器：列表与独立详情承载万行分页；480px行抽屉独立输入包数/吨数，960px回写抽屉容纳未入账单号/数量/实扫对照（4的倍数，默认token，无内部CSS覆盖）；五列分组避免1280下固定列遮住差异。输入失败不关抽屉，不清原因。
- 备选：全程锁DB会阻断扫码和其他作业，不采用；允许确认并自动修正快照需完整实物时点规则，尚无证据，不采用；未入账默认自动放行会把快照后的收发算入差异，不采用。PDA补传/冻结不暂停，但预览token绑定最新未入账清单，回写前持相关单据锁复验。
- 人工门禁：快照后未确认入库登记量、出库计划与实扫量分别展示；默认409。显式确认“按快照时点口径回写”要求实盘排除后续收发影响，并将完整清单、token、原因和operationId留审计。新单/修改/补传改变token，旧勾选失效，不是短装超发的差异放行。
- 测量与证据：tests/e2e/stocktake.spec.ts验证原键恢复、未入账默认阻断/重核、遗忘入口；10000行独立SQL对快照/实盘/delta/前后值，mismatches=0；20同键全200、异键1成功19冲突，均1笔操作；7阶段失败无残留。前端性能分别记开发模式及正式构建30个冷上下文，数值见ACCEPTANCE；人工录入耗时待实测。
- 风险/回退：全局writer短事务会让其他仓暂时等待（实测值见ACCEPTANCE），不是盘点期间跨仓业务暂停；软删键冲突、外部库存漂移禁止覆盖。009新表全空才可down；有快照即保留历史，禁用新增并前向修复。有进行中盘点时不能换回不识别暂停窗口的旧写服务。
